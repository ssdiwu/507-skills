# 代码行为的边界与验收

本参考把已确认需求和影响证据转成可验证行为，仍由 PRD 保存唯一规格正文。只有跨入口、状态、失败或恢复的差异会改变验收时才展开；不要求建立独立用例库或执行额外访谈。

## 选择真正影响结果的维度

从实际用户路径与当前契约中选择有关的入口、状态、事件、目标、身份、运行环境、数据来源和恢复条件。共用 UI 组件的多个入口分别核对默认值、校验、正式提交与保存结果。没有实际影响的维度省略，不生成全局笛卡尔积。

优先主路径、会改变用户结果的分歧，以及失败、并发、重试或恢复的高风险组合。排除组合时说明使其不可达或等价的约束；没有读到或没有测试不能成为排除依据。

## 区分场景状态

| 状态 | 处理 |
| --- | --- |
| 已接受 | 需求已经确认，写入行为与验收 |
| 未定义 | 先查可查事实；确需用户选择的产品行为返回 grill，解决前不定稿 |
| 有依据排除 | 写清条件、守卫或不变量，防止下游误以为漏做 |
| 本次不涉及 | 说明与当前目标的边界，不承诺测试覆盖 |
| 疑似故障 | 保留证据，交给故障调查；不静默修改需求去迎合实现 |

验收项写清准备条件、用户操作或公开调用、预期结果与失败边界、需要什么证据。没有明确执行环境或可用测试时记录验证缺口，不能把拟写用例、已有测试文件和实际运行成功混为一谈。

## 进入现有 PRD

可直接使用现有 Acceptance Criteria 列表；复杂入口差异才用表格：

| 场景与准备条件 | 操作 | 成功／失败结果 | 必须保持的边界 | 验证接缝与证据要求 |
| --- | --- | --- | --- | --- |
| 按当前目标填写 | 用户路径或公开接口 | 可独立判定 | 按真实契约填写 | 区分计划、已有与已执行 |

具体文件、测试框架、实现步骤和执行结果留给工程交接与验证记录。规格保留稳定的行为约束，不复制工程设计。轻任务已有足够验收依据时直接沿用。
