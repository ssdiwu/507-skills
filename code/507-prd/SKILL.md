# PRD（产品需求文档）

把讨论过的上下文沉淀成 **PRD（产品需求文档）**——回答要解决什么问题、给谁、怎么验证。

将已确认需求变成可持续维护的行为与验收依据，减少执行者重新猜测。`507-prd` 是可选的完整规格化动作；采用规格先行规则的项目，无论是否调用本 skill，产品行为变化都先更新现行规格。小改可只改几句话，不强制新建完整 PRD 或工单；恢复既定行为的修复与不改含义的文字、格式调整无需机械新增规格。

`507-prd` 做的是：**对话/方案 → PRD 需求规格**。

## 覆盖什么

- 从当前对话/方案合成 PRD（不重新访谈，只综合已有信息）
- 把 grill 的对齐结论落成可留档的需求文档
- 为执行提供需求规格基准
- 在已授权的项目迁移中，核对旧方案与实现、验收差异，将仍有效的功能要求整理到唯一现行规格

## 不覆盖什么

- 执行前把方案问透 → 用 `507-grill`（`507-prd` 是对齐的下游：先问清要做什么，再写 PRD）
- 把方案拆成可领取的 GitHub issue → 用 `507-issue`（issue 是可领取的执行单元，PRD 是需求规格，两件事）
- 写面向人的活动、培训、合作或项目方案 → 用 `507-frame`
- 架构审查找重构机会 → 用 `507-inspect`
- 执行编排 → 不在本 skill 范围（`507-prd` 产需求规格，不编排执行）

## 核心纪律（不可违反）

1. **承接已有共识**：综合已确认内容，不重复访谈；可查事实自行核对，只有会影响目标、范围或验收的用户取舍进入 `507-grill`。
2. **用项目语言**：从项目阅读入口找到 `GLOSSARY.md`、共用设计和相关决策依据；迁移前同时读取旧词义权威，防止遗漏或改义。标题与正文使用已确认术语，不固定假设旧术语文件位置。
3. **先确定公开验证入口**：写 PRD 时先确定通过哪个公开接口或用户路径验证功能；优先已有验证入口，必要时才提新的入口。
4. **只写稳定信息**：PRD 默认不塞具体文件路径和代码片段，因为很快过期。只有已经确认、且会约束公开行为或验收的状态机、数据形状或接口契约，才可引用关键原型片段并注明来源。
5. **落点是"要做什么/为什么"，不是"怎么改"**：PRD 描述需求和行为，不规定实现步骤。
6. **一个当前权威**：在 spec 中持续更新同一功能要求；旧 PRD 或实施方案按授权提取有效要求并同步退出旧正文维护，不新建竞争版本。对应 issue 和版本实施安排只摘要并回链完整规格。
7. **正文只保留当前结论**：新决定取代旧要求时直接修正受影响章节；取代背景保留在 issue 评论、Git 历史或 ADR，不让 PRD 同时声明两套相反行为。
8. **要求与证据分开**：已确认目标、当前实现和实际验收分别表达；不以实现缺口删减要求，不把验收清单当作已经通过的记录。

## 文档落点

写入前读取项目规范、根 README 及实际 spec／doc 导航，按内容职责确定唯一落点：

1. 用户明确指定一次性输出位置时服从指定；一次性产物不自动成为项目权威。明确指定其它项目规范时说明其适用范围。
2. 项目内持续维护的功能要求默认进入 `spec/`；已有对应规格时原位更新。简单项目可以按 setup 的精简标准维护 README 中明确的需求章节或短规格，不以文档数量决定归属。
3. 旧功能要求仍在版本方案、旧目录或混合文档中时，先核对当前有效内容和来源。已获相关迁移授权则按 [存量迁移标准](../507-setup/references/project-standard.md)准备候选、验证覆盖，再切换目标正文与引用，清理重复正文或保留明确历史；不能直接复制一份 spec 后继续维护旧文。
4. 当前请求不覆盖迁移所需的旧文件或消费者时，不越权全库搬迁；说明最小迁移范围与影响，受阻部分保持原权威可用，交给 setup 承接。普通局部任务不因此宣称全项目迁移完成，旧布局也不作为长期豁免。

版本实施方案负责分批交付、依赖与验证安排，留在 `doc/`，采用编号结构时为 `doc/40-版本实施方案/`；它引用 spec，不再作为功能规格的默认落点。迁移时不能将旧方案中的历史要求、未勾选项或过期候选自动变成现行需求。

尚未形成唯一产品行为、范围或验收解释时不定稿：用户取舍进入 grill，事实不足进入 explore／research，需耐久追踪时再用 investigation issue。创建或迁移规格时在当前授权内同步直接相关导航，整体地图校准交给 `507-map`；远端回链由已授权的 `507-issue` 处理。切换后同一功能只有一份现行正文。

## 代码行为的边界与验收

跨入口、状态、失败或恢复差异会改变验收时，读取 [行为验收方法](references/behavior-acceptance.md)，使用已经取得的影响证据，选择能代表相关差异的验证场景。区分已接受、未定义、有依据排除、本次不涉及与疑似故障；保留会约束产品行为的结论，不另建完整用例流水线。未定义的产品取舍未解决前不定稿，测试计划与执行证据分别记录。

## PRD 模板

适用：用户说"写 PRD / 把刚才整理成需求 / 形成需求文档"。

流程：

1. 读已有上下文、相关词义和共用设计，核对已确认要求、当前代码与验证状态；新项目没有实现时明确说明。
2. 按文档落点规则找到或确定唯一权威文件；存在对应 issue 时在 PRD 中回链，并把 issue 侧的反向链接交给 `507-issue` 更新，不越权管理远程工单。
3. agent（代理）自行确定测试从哪个公开入口进入：优先项目已有公开接口、用户路径和测试先例；PRD 只保留会约束公开行为与验收的部分，具体测试文件、框架和代码库先例留给实施者的交接说明。只有测试接缝会改变产品行为、权限、成本或风险取舍时，才回到 `507-grill` 让用户决定。
4. 写 PRD；把已确认用户决定写进它实际约束的行为、范围、非目标或验收章节，不另建决策堆。
5. 做局部自检并直接修正文档，再交给下游。

```md
## Problem Statement（问题陈述）

从用户视角描述问题。

## Solution（解决方案）

从用户视角描述解决方案。

## User Stories（用户故事）

1. 作为 <角色>，我希望 <能力>，从而 <价值>。
2. ...

## Confirmed Constraints（已确认约束）

- 已确认且会约束需求或验收的数据模型、公开接口、外部集成、安全边界和兼容契约
- 不列待修改的 module（模块）、文件或实现步骤，不把未经验证的架构设想写成需求
- 尚未确定的工程实现由执行阶段收口；会改变产品取舍或产生难逆转成本时返回 `507-grill`

## Acceptance Criteria（验收标准）

- [ ] <从用户路径或公开接缝可独立判定的成功标准>
- [ ] <失败、边界或恢复行为>

## Out of Scope（非目标）

明确不做什么。

## Further Notes（补充说明）

补充说明、风险或开放问题。
```

## 产物自检

写完 PRD 后，从后续执行者和验收者的视角完整重读一次；发现问题直接修正文档，不把检查清单原样附进 PRD：

- **完整性**：没有 `TODO`（待办）、`TBD`（待定）、空章节或未替换占位符；关键事实缺口没有伪装成确定需求。
- **内部一致性**：Problem Statement（问题陈述）、Solution（解决方案）、User Stories（用户故事）、Confirmed Constraints（已确认约束）、Acceptance Criteria（验收标准）与 Out of Scope（非目标）互不矛盾，项目术语前后一致。
- **范围**：内容足以形成一个可执行目标；多个相互独立的目标已拆开，不把未来可能性塞进本次规格。
- **无歧义**：每项需求只有一种合理解释；角色、触发条件、成功结果、失败结果和边界明确。
- **可验证**：每项用户可见行为都能落到公开接缝或用户路径；验收不依赖内部实现细节。

若仍有会改变需求、范围或验收的关键问题，停止下游路由并回到 `507-grill` 对齐；不要把阻塞性未知项藏进 Further Notes（补充说明）后继续执行。

## 和其他 skill 的边界

| skill | 分工 |
|---|---|
| **prd** | 对话/方案 → PRD 需求规格（本 skill，想清楚要做什么） |
| **issue** | GitHub issue 生命周期；既可在 PRD 前承载调查，也可在 PRD 后承载执行追踪 |
| **grill** | 把方案/改动问透（`507-prd` 的上游） |
| **执行入口** | 编排执行（`507-prd` 产需求规格，不编排执行） |

规格优先时：确认行为 → 更新现行规格（需要完整展开时使用 PRD）→ 建立 / 更新 ready issue（按追踪需要）→ 执行。

调查优先时：investigation issue → explore / research / prototype / grill → 写 PRD（可选）→ 原位升级 ready → 执行。

`507-prd` 和 `507-issue` 的区别：**PRD 是“当前完整需求与验收基准”，issue 是“状态、证据历史和可领取执行单元”**。两者没有固定先后，都存在时互相回链。轻任务可省略完整 PRD 与独立工单，仍按项目规则更新受影响的现行规格。

## 完成与接力

- **完成信号**：需求、范围、用户行为、失败边界、验收标准和测试接缝前后一致，没有需要用户决定的阻塞项；项目内只有一个当前规格正文，文档导航和已知来源链接有效；issue 侧需要补反向链接时已明确交给 `507-issue`。
- **产物**：`spec/` 中持续维护的当前需求与验收基准，或符合精简标准的短规格；授权迁移时附来源与旧入口处理结果；用户明确要求的一次性 PRD 按指定交付。
- **候选出口**：需要调查或跟踪执行时进入 `507-issue`；存在低成本可验证的关键假设时进入 `507-prototype` 并回写结论；已授权且任务足够清楚时直接实施；仍缺用户取舍时返回 `507-grill`。
- **回退条件**：目标用户、产品行为、范围、失败边界或验收方式仍依赖未确认的用户取舍时，停止定稿并返回 `507-grill`；关键项目事实不足时返回 `507-explore`；低成本可观察的技术假设尚未验证、且结果会改变需求时进入 `507-prototype`。不得用 `TODO`、`TBD` 或 Further Notes（补充说明）掩盖会改变需求的阻塞性未知。
- **边界提醒**：`507-prd` 写具体产品应做什么；面向人的活动、培训、合作或项目提案归 `507-frame`。

## 红线

- 不拆 issue 工单（归 `507-issue`）。
- 不写实现步骤（写需求和行为，实现走执行入口）。
- 不空访谈（综合已有上下文）。
- 不塞易过期的文件路径/行号（耐久优先）。
- 不把尚未确认的方向或 `investigation` 内容定稿成项目 PRD。
- 不创建与现有 PRD、实施方案或 issue 正文竞争的第二份完整规格。
- 不在和 `507-issue` 的边界上抢“创建 issue”的工作。
