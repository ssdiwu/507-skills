# 普通测试维护与失败定位

专门处理测试资产和失败诊断。它观察公开行为、缩小失败范围并补足关键覆盖，不承担真实生产 bug 的实现修复。

## 原则

1. 测试公共接口和调用者关心的行为，不锁定私有方法、内部字段或与用户目标无关的调用次数。
2. 沿用项目已有测试框架、命令、命名和目录，不为单个任务引入新测试栈。
3. mock（模拟）只放第三方服务、数据库、时间、随机数、文件系统等系统边界，不 mock 自己的内部协作者。
4. 从已确认目标选择具体输出、状态、错误或副作用，检查目标未达成时断言是否仍会通过。“元素存在”“调用发生”“返回类型存在”或“没有报错”只证明对应局部事实，不能替代内容可读、动作正确或结果可用的目标。
5. 失败先分类，不直接改断言把红灯变绿。
6. 如果测试必须读取大量内部结构或伪造巨大对象，先检查模块是否让调用者承担过多细节，以及公开接口是否便于验证行为。

## 工作流程

### 1. 明确任务

判断是新增测试、运行测试、修失败测试、缩小失败范围，还是覆盖关键边界。确认预期行为、公开入口、已有命令和项目测试约定。

### 2. 读取证据和惯例

修失败测试时先读完整输出，定位首个真实失败。再读相邻测试、fixture（测试样本）、项目说明和局部规范，理解当前测试接缝。

### 3. 选择调用者使用的最高层公开验证入口

优先使用公开 API（接口）、CLI（命令行）、页面或其他真实入口。内部重命名、拆函数或替换实现不应让行为测试失效。

### 4. 编写最小有效测试

先找一个会违反目标、却可能通过现有断言的代表性结果，核对测试能否将它判为失败；按实际风险选择，不机械枚举所有坏实现。保存成功不等于读取或展示正确，相关路径需检查正式读取、恢复和实际使用结果。布局、视觉与语义目标按需验证真实操作和呈现，自动检查不足的部分保留必要人工审查，不承诺全部自动化。

- 测试名描述行为场景；
- 优先主路径、重要边界和关键错误路径；
- 不追求无价值的全组合覆盖；
- partial（局部对象）或故意错类型只允许用于测试构造，不进入生产代码。

### 5. 递进运行

选择能覆盖当前目标与风险的最小测试入口，完成项目要求的测试或构建检查；不要求每次依次跑完单例、文件、包和全库。检查通过后，仅因新变化、失败或具体疑点扩大或重复验证。复用仍对应当前代码、依赖、配置与环境的有效结果，记录命令、结果和首个失败证据。

## 失败分类与路由

- 生产行为不符合既定规格：保留测试作为反馈环，转 `507-fix`；
- 规格已改变：先确认新规格，再更新测试和相关说明；
- 测试过时：只调整测试，使其回到公开行为和当前约定；
- fixture、编译、依赖或环境故障：修测试环境，不伪装成产品行为；
- 用户明确要求 test-first（测试先行）或 TDD（测试驱动开发）：按主入口的授权边界进入测试先行模式。

## 交付

报告新增/修改的测试、覆盖行为、运行命令与结果、失败分类、路由和未覆盖边界。测试稳定后可用 `507-review` 独立审查；用户明确要求提交时再用 `507-release 的本地提交模式`。

## 完成与接力

- **完成信号**：目标行为已有稳定测试或失败已完成可信分类，相关测试层级和构建检查结果已报告。
- **产物**：测试资产、运行证据、失败分类与未覆盖边界。
- **候选出口**：生产行为错误进入 `507-fix`；规格变化进入 `507-grill` / `507-prd`；明确 test-first 请求进入本入口测试先行模式；测试工作完成后进入 `507-review`，用户明确要求提交时再进入 `507-release 的本地提交模式`。
- **回退条件**：环境或 fixture 故障先修反馈环，不通过改断言掩盖真实失败。
