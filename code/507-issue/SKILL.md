# GitHub Issue（issue）

把一个需要追踪的问题放进同一条可演进的 issue 生命周期：

```text
draft（对话草稿） → investigation（调查态） → ready（执行态） → 执行 / 验收
```

事实尚未完全清楚时，可以先用 issue 追踪调查；但只有进入 `ready` 后，正文才可作为直接实施与验收的依据。调查结果通过评论保留证据轨迹，当前正文持续更新为最新状态，不复制出平行工单。

## 三种状态

### `draft`：对话草稿

- 尚未远程创建；
- 用于和用户讲清当前问题、已知、未知、建议状态与元数据；
- 可继续调用 `507-explore` 或 `507-grill` 后重写；
- 不伪造 issue 编号、URL、标签或负责人。

### `investigation`：调查态

- 适合现象已值得追踪，但原因、方向、范围或验收仍需证据的问题；
- 正文必须写清现象、影响、当前证据、有接力价值的尝试与排除项、未知、调查问题、下一证据动作和升级条件；
- 可以被认领调查，但不能被包装成“照此实现”的执行合同；
- 调查证据、测试结果、原型 verdict 和用户决策追加为评论，同时回写正文中的当前结论。

### `ready`：执行态

- 事实前提和用户决策已经充分，新旧决定没有并存冲突；
- 正文包含目标行为、范围、不做、依赖、验收与验证；
- 可被 AI 或协作者直接领取执行，不依赖原聊天；
- 从调查态升级时保留同一 issue 编号和历史评论，并同步状态标签或项目字段。

## 核心纪律

1. **状态必须显式**：草稿和每个远程 issue 都声明当前状态，不让“待调查”正文伪装成可执行工单。
2. **调查与执行共用一个载体**：默认原位升级，不因结论变化另开一条重复 issue；只有调查发现多个可独立验证的结果时才按垂直切片拆分。
3. **正文维护当前结论，评论保留证据历史**：测试输出、调查过程和讨论证据进评论；最新问题定义、结论、范围与验收回写正文。
4. **只把用户决策交给用户**：项目事实由 `507-explore`，外部事实由 `507-research`，低成本可观察假设由 `507-prototype`，产品意图与风险取舍由 `507-grill`。
5. **ready 即执行合同**：必须让接手者不读原聊天也能理解目标、范围和验收；正文按行为写，供跨会话持续使用，并能独立验收。不把文件路径、行号和内部实现步骤当合同。
6. **垂直切片**：执行态 issue 覆盖一条范围窄但完整的用户或调用者路径，能从输入走到可验收结果；不按 schema/API/UI/测试水平拆。
7. **远程元数据始终必填**：无论调查态还是执行态，每个远程 issue 都按仓库现有规范设置并核验合适的 labels（标签）与 assignees（负责人 / 拥有者）。只有当前账号缺少权限时才允许未落地，并必须报告真实错误和待补内容。
8. **证据必须可接力**：凡是由原型、截图、录屏、测试输出、外部研究或用户决策支撑的远程 issue，都必须把对应证据以可访问的远程链接或评论内容一并提交；不得只在当前对话、本地临时目录或 agent 记忆里保留。
9. **失败尝试只记有效信息**：调查态记录“假设 → 动作 → 实际结果 → 新信息”和据此排除的可能；没有产生新信息的重复动作不写入正文，不让下一位调查者重走已经证伪的路径。
10. **规格与追踪不重复**：issue 负责状态、负责人、调查历史和执行追踪；已有 PRD 或实施方案时，正文只保留足以领取的摘要并回链唯一完整规格，不复制维护第二份全文。
11. **决定取代必须可追溯**：用户的新决定取代旧决定时，评论记录旧选择、新选择、关键影响和确认依据，正文只保留当前结论；agent 自行收口的工程决定不得伪装成用户决定。

## 调查态模板

```md
## 状态
`investigation` — 当前用于收集事实，尚不可直接领取实施。

## 现象与影响
- 实际发生了什么：...
- 为什么值得追踪：...
- 复现路径 / 来源：...

## 当前证据
- 已确认：...
- 证据锚点：...

## 已尝试、结果与排除
- <假设> → <动作> → <实际结果> → <得到的新信息>
- 已排除：...

## 未知与调查问题
1. ...

## 下一证据动作
- <读取、测试、research 或 prototype；写目的，不写猜测结论>

## 升级为执行态的条件
- [ ] 原因或约束已确认
- [ ] 用户拥有的取舍已由 grill 确认
- [ ] 范围与验收可写成唯一解释

## 远程元数据
- labels: <仓库已有的最小合适集合>
- assignees: <按仓库 ownership；无约定时当前登录用户>
- metadata_status: complete / permission_blocked
```

尚未产生有效尝试时，删去“已尝试、结果与排除”一节；第一次出现可接力结果后再补，不保留空占位符。

## 执行态模板

```md
## 状态
`ready` — 可直接领取执行。

## 背景与目标
- problem: ...
- goal: ...

## 当前状态与已确认决策
- 用户已确认的产品决定：...
- Agent 收口的工程决定：...
- 完整需求 / 实施规格：<没有独立规格时删除本行；有则提供可访问链接>

## 范围
### includes
- ...
### excludes
- ...

## 关系与依赖
- depends_on: ...
- blocks / related: ...

## 验收与验证
- [ ] <可独立判定的行为标准>
- verification: <公开接缝、用户路径或项目既有检查>

## 远程元数据
- labels: <仓库已有的最小合适集合>
- assignees: <按仓库 ownership；无约定时当前登录用户>
- metadata_status: complete / permission_blocked
```

没有用户决定或独立规格时删除对应行，不保留空占位符。区分决定来源是为了防止后续 agent 把工程设计重新抛给用户，或把 agent 判断误写成用户承诺；不是要求给每句话添加标签。

## 证据交接

远程 issue 不只要写出结论，还要让下一位 agent / 协作者不读原聊天也能复查结论从哪里来。先判断本 issue 是否依赖证据；没有证据的纯文本需求不强行制造附件。

### 什么算可接力证据

- **原型 / 视觉决定**：至少提供可查看的静态图（截图、录屏帧或设计稿）和可继续编辑的源文件（HTML、设计文件或等价源）；评论说明它支持哪条产品决定。
- **测试 / 运行结论**：提供可定位的 CI（持续集成）链接、日志摘要或可复跑命令与结果；不能只写“已验证”。
- **研究 / 用户反馈**：提供原始链接、必要的时间锚点与最小相关摘录；敏感聊天只保留经授权的最小化结论，不复制私密原文。
- **用户决策**：首次确认时在评论中记录选项、已选结果与关键取舍；发生取代时同时记录旧结论、新结论、影响和确认依据；正文只回写当前结论。

聊天内的临时预览、本地绝对路径和未回链的 agent 产物都不算远程证据。私密但持久可访问的链接可以使用；如果仓库政策不允许外链，就把最小必要的源码、图片或摘要直接放进 issue 评论。

### 提交顺序与核验

1. **先准备**：在创建 / 更新 issue 前产出截图、可编辑原型、日志或研究链接。
2. **再提交**：创建 / 更新正文和元数据后，把证据与决策背景写入评论，并从正文或评论彼此回链。
3. **最后核验**：重新读取远程 issue，确认链接、图片或源码实际出现在 issue 中，且能独立说明结论。

若证据尚未可上传，必须在 issue 明确标为待补，不能声称“原型已附”或“已经提交完成”。

## 生命周期工作流

1. 读取仓库 `AGENTS.md`、贡献规范、issue 模板、现有标签、ownership 与少量同类 issue。
2. 判断当前应停在 `draft`、创建 `investigation`，还是直接创建 `ready`；在对话中说明判断依据。
3. 草拟正文并做状态对应的自检；若有原型、研究或验证结论，先准备可接力证据包。
4. 创建或更新远程 issue 时设置标签和负责人，再回写证据与决策背景；已有 PRD / 实施方案时在 issue 中链接唯一完整规格，不复制全文，规格侧缺少 issue 来源链接时报告并路由给 `507-prd`；创建后读取远程状态、元数据和证据链接核验。
5. 调查态按下一证据动作推进：把详细证据写评论，把当前结论、有效尝试、已排除可能和未知回写正文。
6. 满足升级条件后，把同一 issue 改写为执行态模板，更新状态标签/字段并再次核验元数据。
7. 执行完成后由项目既有流程验收和关闭；本 skill 不代替实现。

## 远程元数据

- 用仓库实际规则和 `gh label list` 选择已有标签，不套用固定词表，不未经授权创建新标签。
- 按 ownership 或分派约定选择负责人；没有约定时用 `gh api user` 确认当前登录用户，用户明确指定时以指定为准。
- 创建后用 `gh issue view <number> --json labels,assignees` 核验；状态变化后再次核验状态标签或项目字段。
- 找不到合适标签时，在创建前报告标签体系缺口；只有仓库规则或用户授权时才创建标签。
- 权限失败时保留已经创建的 issue，报告 URL、真实权限错误、待补标签和负责人，并标记 `permission_blocked`；不得声称已收口。

## 自检

- 状态与正文成熟度一致；调查态没有假装可执行，执行态没有遗留 `TODO`、`TBD` 或“方向待定”。
- 不读原聊天也能理解现象/目标、当前状态、范围、未知或验收。
- 调查问题能由具体证据动作回答；执行态每条验收都可独立判定。
- 调查态只保留产生新信息的有效尝试，实际结果与排除项足以避免重复走已证伪路径。
- 标题、正文、评论结论、标签、负责人和状态字段没有互相冲突。
- 用户决定与 agent 工程收口的来源可区分；决定发生取代时正文是当前真相，评论能追溯变化。
- 多个独立结果已按垂直切片拆分，依赖使用真实编号。
- 若 issue 依赖原型、测试、研究或决策证据：静态查看入口与可编辑 / 可复查来源均已远程回链；没有只留在聊天或本地的关键证据。

## 完成与接力

- **完成信号**：草稿已明确下一状态，或远程 issue 已创建/更新且状态、正文、标签、负责人、证据链接完成核验；权限阻塞时有完整待补清单。
- **产物**：对话草稿或同一条持续演进的 GitHub issue，以及调查评论与可接力证据形成的历史。
- **候选出口**：调查态进入 `507-explore`、`507-research`、`507-prototype` 或 `507-grill` 后回写；需要独立耐久规格时进入 `507-prd`，再回写并原位升级；执行态进入相应实施入口；完成后进入 `507-review` 和项目验收；只要求记录时可停在已标明状态的 issue。
- **回退条件**：ready 阶段发现事实或用户决策仍未定时，降回 investigation 并说明原因，不继续伪装成执行合同。

## 红线

- 不为调查和执行默认创建两条重复 issue；
- 不把未验证猜测写成 ready 的方向或验收；
- 不把 issue 写成逐文件实施步骤；
- 不把“原型已做 / 测试已跑 / 用户已确认”写进 issue，却只把对应证据留在当前聊天或本地；
- 不跳过标签、负责人和远程核验；
- 不因缺权限自行修改仓库权限或伪造完成。
