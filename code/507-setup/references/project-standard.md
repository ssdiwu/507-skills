# 项目标准规范

这份规范适用于主动维护型代码项目。

目标是让任何 agent 进入一个项目时，先能找到：入口、文档地图、项目语言、关键决策，以及各代码目录的职责说明。

## 必备项

### 1. `AGENTS.md`

项目级 agent 规范文件，必须存在。

应包含：

- 项目一句话定位
- 先读文档顺序
- 代码边界与安全边界
- 验证方式
- 项目特有禁忌或不做事项
- **代码工程纪律**（适用于含代码的项目，由项目初始化流程写入）：
  - **最小实现梯子**：先判断是否真需要，再依次检查项目已有实现、标准库、平台能力、已安装依赖和成熟且维护良好的新依赖；读取实际版本的文档、类型定义或做最小验证，在第一个能完整满足当前需求的层级停止，最后才写最小自有实现。
  - **结构服从真实边界**：模块按职责、变化原因、生命周期、外部系统或副作用划分。删除后复杂度消失的透传层应移除；重复次数、实现数量和代码行数只能提供证据，不能替代边界判断。
  - **可用基线与安全替换**：从最小可用的端到端切片开始，每次只增加一个已验证能力；替换已有可用产物时，先隔离生成并验证候选版本，成功后再整体切换，失败时保留上一版。
  - **单路径演进**：确认没有真实消费者后，删除旧内部路径及其实现、配置、文档和专属测试；只有公开 API（接口）、存量数据、已发布客户端或滚动升级确有需要时，才建立范围明确、有期限、有退出条件的过渡路径。
  - **难逆转选择面向长期**：数据模型、公开契约和安全边界服从已确认的长期约束；原型、故障止血和迁移窗口必须隔离、可验证且有退出条件，生产核心不得以日后整体重写为前提。
  - **测试看行为**：测试优先通过公共接口验证行为，不测内部实现；mock 只放在系统边界。
  - **先建反馈环再调 bug**：调 bug 先造一个快速、确定性、agent 能跑的 pass/fail（成败）信号（失败测试/curl/CLI 重放/headless 等）；没有反馈环就继续缩小范围或补充观测，不盯着代码空猜。信号是 90% 的调试，其余是机械操作。
  - **失败后换轨**：每次失败记录原始信号、当前假设、执行动作、实际结果和新增信息；连续两次出现同类失败且没有缩小范围时，停止同路径重试，完整读取错误与相关源码，核验版本、路径、依赖等前置假设，建立最小复现并切换本质不同的假设。仍无法解决时，报告已验证事实、已排除可能、当前问题边界和真正需要的用户输入。
  - **插桩打 tag**：所有临时 debug 日志打唯一前缀 tag（如 `[DEBUG-a4f2]`），清理时一个 grep 全删；未打 tag 的临时日志会残留。

不应包含：

- 冗长的背景故事
- 大段重复文档地图
- 术语表正文
- 架构决策全文

### 2. `README.md`

项目入口说明，必须存在。

应回答：

- 这是什么项目
- 给谁用
- 怎么运行
- 目录怎么分
- 主要入口在哪

### 3. `doc/`

项目知识目录，必须存在。

最少应有 `doc/README.md`。

`doc/README.md` 应该说明：

- 这套文档有哪些
- 先读什么、后读什么
- 哪些是当前实现权威
- 哪些只是历史归档

主动维护型项目默认采用编号目录组织 `doc/`，除非项目很小（少于 5 个文档）或已有清晰历史组织方式：

| 段 | 职责 | 权威性 |
|---|---|---|
| `00-产品与原则/` | 产品定位、目标用户、体验原则、UI 气质；同类材料达到多个时从 `doc/` 根目录收拢到这里 | 长期有效权威 |
| `10-架构与运行/` | 当前架构、代码现状、运行、测试、开发规范 | 当前实现权威 |
| `20-能力参考/` | 外部能力事实库、调研、实测数据、license、能力边界 | 事实参考，不决定排期 |
| `30-路线图/` | 版本维度编排、后续计划 | 路线图唯一权威 |
| `40-版本实施方案/` | 已确认、需要耐久指导交付的 PRD、版本 / Build 规格与专项实施方案；必须含可判定的验收或 checklist | 当前交付与验收权威，受路线图约束 |
| `90-归档/` | 已被取代、已放弃、合并后的旧草案，或只用于追溯历史背景的材料 / 日志 | 否，仅查历史事实 |

不是每个项目都必须创建所有编号目录；只创建有实际内容的段。产品介绍等单一入口文件可以留在 `doc/` 根目录，形成多份同类材料后再收拢。若已有路线图、PRD 或版本实施方案，就不应继续平铺在 `doc/` 根目录，应放入对应编号段。

### 文档按职责与阶段路由

`doc/` 按“这份内容负责什么”分类，不按“文件已经完成没有”机械搬运：

```text
尚未确认的想法或需求
  → 对话或 investigation issue
已确认、仍需跨会话追踪的需求
  → ready issue 正文
需要成为耐久交付与验收基准
  → doc/40-版本实施方案/ 中的 PRD、需求规格或实施方案
已经落地的当前产品 / 代码 / UI / UX 事实
  → doc/00-产品与原则/ 或 doc/10-架构与运行/ 的对应当前权威
已完成且用户可感知的变化
  → CHANGELOG.md
已被取代、放弃或只供追溯的材料
  → doc/90-归档/
```

- `issue` 负责状态、调查轨迹、负责人和执行追踪；正文维护当前结论，评论保存证据与决定变化历史。
- PRD / 需求规格负责稳定描述问题、产品行为、范围、非目标、验收和测试接缝；存在对应 issue 时，在双方互相回链，不复制维护两份完整需求。
- 实施方案负责当前 Build 或专项如何分批交付、验证和收口；同一交付已有权威方案时，优先把 PRD 章节并入或更新该文件，不再创建平行规格。
- 已完成的需求规格或实施方案只要仍是有效验收基准，可以留在 `40-版本实施方案/` 并由目录 README 标明状态；完成本身不等于归档。
- ADR 解释难逆转决定为什么成立；它不能替代当前规格。新 ADR 取代旧 ADR 时保留旧文件并维护取代关系。

### PRD 落点

写 PRD 前先读 `doc/README.md` 和目标目录 README：

1. 项目已有明确的产品规格或交付方案入口时，遵循现状并更新唯一权威文件。
2. 项目采用本编号结构、且需求已经确认到足以成为执行与验收基准时，默认写入 `doc/40-版本实施方案/`；文件名和内部编号遵循该目录现状。
3. 少于 5 份文档的小项目可以直接使用 `doc/<主题>产品需求.md`，但 `doc/README.md` 必须标明其职责和权威性。
4. 尚未确认、未形成唯一解释或仍需要调查的内容，不定稿成 PRD；留在对话或 `investigation` issue，收敛后再写。
5. 用户明确指定一次性输出位置时遵从指定，但不把一次性文档伪装成项目当前权威。

创建或移动 PRD / 实施方案时，同步目标目录 README 与 `doc/README.md`；不得同时保留旧路径和新路径两份正文。

## 条件必备项

### `CHANGELOG.md`

主动维护型代码项目应从开局建立 `CHANGELOG.md`，即使尚未发布或尚未实现；它记录每个版本的用户/使用者可感知变更（功能、修复、破坏性变更、迁移说明）。采用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 基本格式，版本以 Git tag（Git 标签）为准。

适用：会持续演进的对外库、CLI、SDK、应用、多人项目，以及计划发布但仍处于设计或首个实现阶段的项目。
可明确豁免：一次性原型、明确不再维护的实验或私人临时脚本。

首次建立时只创建标题、格式说明与 `## [Unreleased]`（未发布）段；不为此倒填历史提交。后续用户/使用者可感知变更先写入该段，发版时再固化为带日期的版本段。

写法要求：

- 按版本倒序，最近版本在最上。
- 每条变更用**用户/使用者能感知**的语言，不写"重构了内部模块 X"。
- 区分类型（Added / Changed / Fixed / Removed / Breaking），保持格式一致。
- 破坏性变更必须显式标注，并给出迁移说明。
- 不写未发布的内部计划；路线图归 `doc/30-路线图/`。

不写：

- 提交粒度的完整 git log
- 实现细节
- 临时方案

### `doc/术语表.md`

当项目存在稳定的领域词、系统词或经常混用的概念时，应建立 `doc/术语表.md`。

它只做一件事：定义“这个项目里这个词精确指什么”。

写法要求：

- 定义写“它是什么”，不是“它做什么”。
- 同一概念只保留一个规范叫法。
- 其它常见但不推荐的叫法，放进 `_Avoid_`（禁用同义词 / 别名）。
- 只收项目语言，不收通用编程概念、模块名或类名，除非它们本身就是领域词。

不写：

- 实现细节
- 临时方案
- 决策讨论过程
- 草稿内容

### `doc/决策档案/`

当出现同时满足以下三条的决定时，应建立 `doc/决策档案/` 并记录：

1. 难逆转
2. 没有上下文会让人困惑
3. 存在真实权衡

如果只是小约定、临时实现或普通笔记，不进 ADR。

文件与索引规则：

- **文件命名**：`0001-中文标题.md`。编号前缀保顺序，标题用中文描述决策主旨；项目专有术语沿用 `doc/术语表.md` 的规范叫法（不强行中英互译），如 `0006-建检循环与三层结构.md`。
- **索引**：维护 `doc/决策档案/README.md`，每条一行：编号 + 标题 + 一句话主旨（写「定了什么」不写「为什么」，不超过一行）。新增或更新 ADR 时同步索引；索引失真即视为文档债。
- **何时建索引**：第一条 ADR 落地时就建 `README.md`（1 条也建）。`doc/README.md` 的决策档案那行只指向 `doc/决策档案/README.md`，不再逐条罗列，避免两处重复维护。

### `doc/经验笔记.md`

收"可改的做法与避坑经验"，回答"这事儿怎么做"。与术语表、决策档案按边界分工：术语表收词，决策档案收不可逆决策，经验笔记收可改做法。

**准入门槛**：解决一个坑时，如果换一个无上下文的 agent 来会重走一遍，就值得记。不满足 ADR 三条、也不是词的定义，但下次还会用到的经验走这里。

**条目格式**：现象 + 做法 + 证据（日志路径 / commit / ADR 指向）。

**维护**：重复发生时在原条目追加证据；做法被推翻就改这条。惰性创建，没值得记的经验就不建空文件。

### 含代码目录的 `README.md`

任何包含代码的目录都应有自己的 `README.md`，尤其是：

- `src/`
- `tests/`
- `scripts/`
- `bin/`
- `packages/`
- `apps/`
- 其它项目特有代码目录

## 命名约定

- 项目术语表统一使用 `doc/术语表.md`
- 不再默认使用 `glossary.md`
- 如果项目历史上已有 `docs/`，优先迁移到 `doc/`，或明确说明为何保留

## 项目初始化顺序

推荐按这个顺序落地：

1. `AGENTS.md`
2. `README.md`
3. `doc/README.md`
4. `doc/` 编号目录地图（按需创建 `00 / 10 / 20 / 30 / 40 / 90`）
5. `doc/术语表.md`
6. `doc/决策档案/`
7. `doc/经验笔记.md`（惰性，有经验才建）
8. 各代码目录 `README.md`

## 通过标准

一个项目只有在下面这些点上同时成立，才算符合标准：

- agent 进来能知道怎么读
- 人进来能知道这是什么、怎么跑
- `doc/` 能区分当前实现、路线图、PRD / 版本实施方案和历史归档
- 项目语言有统一叫法
- 关键决策能找到出处
- 代码目录不会失去职责说明

## 例外

只有用户明确说明时，才允许偏离这份标准。
