# 项目标准规范

这份规范用于主动维护型代码项目的初始化与全量巡检。目标是让人和 agent 找到真实入口、权威关系、项目特有边界与可复验命令，而不是让所有仓库拥有相同篇幅和目录。

## 1. 事实优先与项目形态

任何规范结论都先由当前 checkout、manifest、源码、测试、运行配置和实际验证核实。文档解释意图；当前行为以实现和证据为准。

### 完整合同

适用于持续维护的应用、服务、公开库或多模块项目，通常存在多个运行边界、外部系统、持久化、安全/合规风险、发布面或耐久文档。

### 精简合同

适用于单入口扩展、小型包、一次性原型、临时验证目录或职责单一的内部工具。精简合同仍必须说清项目边界、真实验证、安全/副作用和外部动作授权，但不复制与项目无关的通用工程教材。

### 受保护范围

以下内容默认只识别和报告，不自动改写：

- 框架或工具生成的 `AGENTS.md` / `CLAUDE.md`；
- 嵌套项目、子模块或团队自己维护的分层规范；
- 测试 fixture、冻结样本、快照和验证副本；
- 其它 worktree、归档、历史 demo 和只读参考实现。

只有用户明确点名且已核实维护方式时才能纳入；生成文件必须通过其生成源更新，不能直接改产物。

选择能完整覆盖真实风险的最轻合同。项目很大不自动等于完整合同，文件很少也不自动等于低风险。

## 2. `AGENTS.md`

主动维护且宿主会读取项目规则的代码项目应有项目级 `AGENTS.md`。已有生成机制或上级/下级权威时，先遵循其所有权关系。

### 完整合同建议结构

1. 项目定位与权威来源；
2. 阅读路由；
3. 任务、范围与失败边界；
4. 项目特有工程、安全、数据或外部系统约束；
5. 与改动相称的真实验证；
6. 文档维护与 Git / 发布授权。

### 精简合同建议结构

1. 项目边界与必读入口；
2. 项目特有安全或副作用约束；
3. 真实命令、验证边界与外部动作授权。

结构是检查清单，不是固定标题模板。相邻内容可以合并；不为凑章节重复同一句话。

### 必须成立

- 平台、运行时、入口、公开能力和命令由 manifest、源码或运行证据核实，不从项目名、旧 README 或任务描述猜测。
- 只写跨任务稳定且项目特有的约束。全局沟通、通用安全和宿主调度留在各自权威，不复制进每个项目。
- 路径优先写仓库相对路径；本机绝对路径只能作为被检测并等待迁移的风险类别，不能成为长期操作说明。
- 验证命令必须真实存在，并区分静态检查、构建、自动测试、联网验证和人工验收。
- `commit`、`push`、`tag`、`publish`、`deploy`、商店提交、生产抓取和外部系统写入必须有明确授权边界。
- 已知实现若仍违反目标安全边界，规范必须写明“当前缺口、禁止动作、修复条件与出口”；不能只写理想规则并暗示实现已安全。

### 不应包含

- 当前版本号、分支、Issue、PR、端口、服务器、临时任务、进度、负责人或时间快照；
- 凭据、资源标识、个人路径、账号、私有数据或可从中恢复敏感值的示例；
- 冗长背景故事、术语表正文、ADR 全文或大段文档地图；
- 固定 Skill 路由表、宿主专属命令或与项目无关的通用工程纪律；
- 未运行验证的“已通过”声明，或对尚未修复风险的“安全/可移植”承诺。

版本、命令和能力需要提及时，指向各自当前权威（如 `package.json`、plugin manifest、Git tag、CHANGELOG 或实现），不在 `AGENTS.md` 复制易漂移值。

## 3. 根 `README.md`

持续使用、需要人类进入的项目应有根 README；一次性原型、设计画布或临时验证若已有更直接且明确的入口，可以在巡检报告中说明豁免，不为形式完整创建空 README。

README 应按项目实际回答：

- 这是什么、给谁使用；
- 最小运行/安装方式和前置条件；
- 主要入口、目录职责与上下游；
- 当前权威在哪里，哪些内容只是历史或生成产物。

README 不保存“当前仍在某阶段”等会快速失效的进度句。版本号确有用户价值时指向 manifest、registry、Git tag 或 CHANGELOG 的唯一权威；未发布版本不得冒充已发布状态。

## 4. `doc/` 与文档地图

`doc/` 不是所有项目的强制骨架。满足任一情况时才需要耐久文档地图：

- 项目已有多份长期文档且职责可能混淆；
- 当前实现、产品规格、能力事实、路线图和历史材料需要分开；
- 跨会话协作需要稳定阅读顺序和权威关系。

小型包或原型只有少量说明时，可以由根 README 承担地图。已有 `docs/` 或其它清晰组织方式时优先沿用，不为了命名统一机械迁移。

需要 `doc/README.md` 时，它至少说明：文档有哪些、先读什么、当前权威是什么、什么只供历史追溯。

### 编号目录（按需）

项目采用编号结构时，只创建有真实内容的段：

| 段 | 职责 | 权威性 |
|---|---|---|
| `00-产品与原则/` | 产品定位、目标用户、体验原则和稳定产品事实 | 长期产品权威 |
| `10-架构与运行/` | 当前架构、运行、测试与开发边界 | 当前实现说明 |
| `20-能力参考/` | 外部能力、调研、实测、license 与能力边界 | 事实参考，不决定排期 |
| `30-路线图/` | 版本维度安排与后续计划 | 路线图唯一权威 |
| `40-版本实施方案/` | 已确认且需要耐久指导交付的 PRD、规格与实施方案 | 当前交付与验收权威 |
| `90-归档/` | 被取代、放弃或只供追溯的材料 | 历史参考 |

完成状态不决定归档：完成但仍是有效验收基准的规格可以留在职责目录并标明状态；只有被取代、放弃或纯追溯材料进入归档。

### 文档职责路由

```text
尚未确认的想法或需求
  → 对话或 investigation issue
已确认、仍需跨会话调查或执行
  → ready issue 正文
需要成为耐久交付与验收基准
  → 项目既有规格入口；无入口时进入 PRD / 实施方案
已经落地的产品、代码、UI / UX 事实
  → 当前产品或架构权威
已完成且用户可感知的变化
  → CHANGELOG.md
已被取代、放弃或只供追溯
  → 归档
```

- Issue 负责状态、调查轨迹、负责人和执行追踪；正文维护当前结论，评论保留证据历史。
- PRD / 需求规格负责问题、产品行为、范围、非目标和验收；存在对应 Issue 时互相回链，不复制两份全文。
- 实施方案负责当前版本或专项如何分批交付、验证和收口；已有唯一方案时更新原文件。
- ADR 解释难逆转决定为何成立，不能替代当前规格。

创建、移动或改名地图文档时由 `507-map` 校准入口和链接，不在 setup 中顺手搬迁整棵文档树。

## 5. `CHANGELOG.md`

对外发布、持续演进且有用户可感知变化的应用、库、CLI、SDK 或多人项目应维护 Keep a Changelog 格式的 CHANGELOG，版本以 Git tag 或发布 registry 为准。

一次性原型、临时验证、未计划发布的私人脚本或完全内部生成物可以豁免。没有真实变化时不为初始化倒填历史。

CHANGELOG：

- 记录用户/使用者可感知的 Added、Changed、Fixed、Removed 与 Breaking；
- 不复制 Git log、内部重构、临时计划或未验证的未来承诺；
- 未发布变化进入 `Unreleased`，发布时再固化版本和日期。

## 6. 术语、决策与经验

这些文件按需要惰性创建：

### `doc/术语表.md`

只定义项目稳定领域词“是什么”。统一规范叫法，把不推荐同义词列入 `_Avoid_`；不收通用编程词、实现细节或讨论过程。

### `doc/决策档案/`

只有同时满足“难逆转、缺少上下文会困惑、存在真实权衡”的决定才进入 ADR。采用顺序编号并维护索引；新 ADR 取代旧 ADR 时保留历史并标明关系。

### `doc/经验笔记.md`

记录可修改、下次仍会复用的做法与避坑，格式为“现象 + 做法 + 证据”。不满足准入门槛时不创建空文件。

## 7. 分层 README

不是每个含代码目录都需要 README。只有出现真实导航边界时才建立，例如：

- 目录有独立职责、生命周期、外部系统或公开入口；
- 多个消费者需要理解该目录契约；
- 运行、生成、迁移或测试方式无法从根 README 与 manifest 看清；
- 目录内容经常因职责不明被误改。

单一实现目录、直观的 `src/`、小型 `tests/` 或只含辅助脚本的目录，不为形式完整强制建 README。分层 README 只说明职责、入口、上下游和局部验证，不复制根地图。

## 8. 初始化与巡检顺序

1. 冻结项目根、worktree、工作区状态、目标和排除项；
2. 识别生成文件、嵌套规范、fixture、快照、归档和历史副本；
3. 读取现有 README/doc 地图、AGENTS、manifest、入口、测试和安全配置；
4. 选择完整合同、精简合同或保持受保护；
5. 报告事实冲突、规范漂移、现存代码风险和推荐路由；
6. 获得授权后只更新项目合同；地图交给 `507-map`，代码风险交给相应实现 skill；
7. 验证链接、路径、命令、差异范围和未覆盖边界。

## 9. 通过标准

项目符合标准时，应同时成立：

- agent 能知道先读什么、当前权威是什么、哪些范围不能改；
- 人能找到项目定位、入口和真实运行方式，或有证据支持的轻量豁免；
- `AGENTS.md` 不含动态快照、个人环境、凭据或重复全局模板；
- 项目特有安全、数据、外部副作用和验证边界清楚；
- 现存实现风险被如实标注并有阻断，不被规范文字掩盖；
- 文档按真实职责存在，不因形式完整制造空目录或第二权威；
- 受保护范围没有被误写；
- 构建、自动测试、联网验证、人工验收、提交和发布结论各自绑定实际证据。

## 例外

项目现有组织、生成机制或明确用户决策可以偏离本标准。例外必须写清依据、影响和维护方式；不能只因样例不同就强制迁移。
