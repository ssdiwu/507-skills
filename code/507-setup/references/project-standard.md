# 项目启动与规范迁移标准

本标准规定项目应具备的工作依据、各类内容的唯一归属、工程前提和存量迁移要求。新项目直接采用，已有项目在选定范围内主动迁移；按实际用途裁剪文件，不以已有布局清楚或使用已久为保留旧标准的理由。

## 1. 适用范围与事实边界

先确定项目类型、当前阶段和下一步要完成的结果。持续维护的应用、服务或库使用完整合同；入口与风险确实简单的工具或原型可用精简合同。文件数量和代码行数不能代替风险判断。

- 项目目标与已确认要求说明“应该怎样”；源码、配置说明“目前怎样实现”；运行与测试证据说明“实际验证到哪里”。分别核对，不因实现缺失删除要求，也不把规格写完视为功能完成。
- 新项目没有源码或命令时，明确尚未建立的入口及其影响。探索、设计、隔离验证与正式实现有不同前提，不要求写代码前已经完成所有未来设计。
- 全局规则只在用户明确指定目标后处理；项目初始化不自动授权修改全局文件、其他项目或外部系统。
- 生成文件、嵌套权威、第三方原件、测试 fixture、冻结快照、归档和其它 worktree 是受保护范围。识别其所有权和引用，不为了统一外观改写；生成规则通过生成源维护。

## 2. 开工依据

各项至少应有明确答案、证据或会阻止哪一步的缺口。文件和目录只在有真实内容与消费者时建立。

| 依据 | 最低需要回答 | 默认归属与适用条件 |
|---|---|---|
| 目标与范围 | 给谁使用、解决什么问题、下一步结果与明确排除项 | 根 README 摘要并回链；详细产品要求进入 spec |
| 协作规则 | 先读什么、按哪个基线、怎样变更和验证、哪些动作需授权 | 项目 AGENTS；生成或继承关系明确时遵循维护入口 |
| 共同语言 | 核心对象是什么、关系如何区分、哪些叫法不能混用 | 有领域概念时建立 GLOSSARY |
| 共用设计 | 信息层级、排版与密度、控件角色、反馈、无障碍和适配 | 有界面且需要共用设计约束时建立 DESIGN |
| 下一条完整路径 | 用户动作、系统行为、状态归属、失败与恢复、可判定的验收 | 相关 spec；库和无界面工具可用调用者路径／公开接口场景 |
| 长期知识 | 外部依据、架构说明、取舍理由、长期规划与历史在哪里 | 有实际材料时建立 doc 及必要导航 |
| 工程与验证 | 怎样准备环境、运行和验证，当前检查覆盖什么，还缺什么 | 实际配置／脚本／测试为事实源，README 提供入口 |

小型项目允许在 README 的明确章节中承载少量职责，按需链接短规格；不创建空 DESIGN、GLOSSARY、doc 或 ADR。内容开始混淆或出现独立维护需求时拆入对应位置。精简合同使用同一职责划分，不继承旧规范作为另一套长期标准。

## 3. 文档职责与维护

### README：定位与真实入口

说明项目是什么、给谁使用、范围、前置条件、最小运行方式、目录职责及按问题阅读的入口。可保留使用者必须知道的能力限制，但动态任务进度、负责人和验收记录进入各自载体，不在 README 维护第二份快照。

开发与验证命令必须能定位到实际配置或脚本，区分存在、已运行及通过。版本有必要提及时链接 manifest、tag、registry 或 CHANGELOG 的实际权威，不能把未发布版本描述为已发布。

分层 README 只在存在独立职责、生命周期、运行方式或真实导航边界时建立；说明入口、上下游、写入所有者和局部验证，回链相关规格，不复制产品要求。

### AGENTS：工作规则与授权

**全局层**仅保存跨项目稳定的沟通、工作纪律和安全底线。目标文件和来源明确，不写项目事实、当前任务、版本、分支、端口、账号、凭据、个人路径或宿主命令与加载机制。全局示例供用户按需修改，不会自动覆盖用户配置；项目特有规则在项目内优先。

**项目层**保存跨任务稳定且项目特有的定位、阅读路由、变更要求、安全与数据边界、验证责任、文档维护和外部动作授权。根 README 维护具体命令与目录说明，AGENTS 引用入口并规定如何使用。

按项目实际补清以下边界；全局已有纪律只引用，不逐条复制到项目规则：

- 新任务、切换工作树和跨会话续办时核对目录、分支、本地改动、相关规格、用户改稿与最新确认；涉及远端协作时核对相关分支，未核实则说明；不因发现新提交自动切换、合并或覆盖。
- 已确认的产品行为变化先更新对应现行规格，再实施；小改可只改几句话。恢复既定行为的修复、不改含义的文字或格式调整，无需机械新增规格。
- 当前要求、实现与验证不同步时查证差异，不静默降低要求，不擅自恢复已排除内容。
- 保护本地改动、数据、凭据与公开契约。同一工作树一个写入者；需要并行写入时使用隔离工作树，集成后再验证。
- 根据实际风险执行必要验证，分别报告构建、自动测试、真实运行、人工验收、提交和发布；已知安全缺口写清影响、禁止动作和修复出口。

不将易变版本、分支、issue、端口、服务器、进度或个人环境写成长期规则，不复制全局纪律、术语正文、完整设计或技能路由表。commit、push、tag、publish、deploy、商店提交、生产抓取和外部系统写入必须有明确授权边界。

### GLOSSARY：项目词义

默认使用根 `GLOSSARY.md`，中文标题为“<项目名> 术语表”。定义稳定领域对象及容易混淆的概念，采用规范叫法，必要时注明避免混称；不收通用编程词、操作流程、实现类名、视觉参数或临时状态。

“某对象是什么”属于这里；“操作后怎样变化”进入 spec；“为什么选择这种对象关系”进入 doc 中的设计依据。迁移旧术语表或 CONTEXT 时先分类内容，不把其中全部上下文整份移成词义。未切换前从实际导航读取旧权威，切换后只维护 GLOSSARY；不增加同内容的上下文文件。

### DESIGN：共用体验与视觉规则

有界面项目记录跨功能的体验目标、信息层级、排版与密度、控件角色、反馈、无障碍、主题及平台／语言适配要求。维度由项目目标决定，不给所有项目强制同一语言、设计风格、组件库或数值。

共用细则可由 DESIGN 指向唯一正文；具体页面、操作和局部验收进入 spec。实现前明确控件、层级与反馈分别表达什么，以及已确认的体验目标，实现后定位共享组件／样式入口，核对实际值和真实布局。参考、候选、定案和已验证效果分别标明；原型不能自动替换基线，构建通过不证明体验符合要求。

### spec：持续维护的现行功能规格

`spec/` 按功能或完整用户路径维护已经确认的产品行为、页面／交互状态、接口边界、失败与恢复、非目标和验收标准；PRD 是需要充分展开时的表达方式。优先原位更新，避免每轮创建平行版本；不以文档长短或是否调用 prd 技能决定是否维护要求。

首批功能实现前，至少明确本轮完整路径及相关验收；不要求提前编造整个产品的未来规格。已确认但未实现的目标和实际覆盖分别标明，未决产品取舍先对齐；库或服务同样通过公开调用场景定义行为。

稳定或已经交付的功能继续在 spec 维护。变化频率不决定归属；版本实施方案保存交付安排，不能与 spec 同时维护同一功能的两套当前正文。`spec/README.md` 在多份规格需要导航时提供按功能／路径的入口，并回链设计、词义、实现和验证位置。

### doc：依据、说明、规划与历史

保存长期参考、研究、架构与运行说明、设计思考、取舍理由、长期规划和实施安排。有多份材料需要导航时建立 `doc/README.md`；没有实际内容时不创建目录或空分段。

研究标明来源、版本与适用边界，不能直接变成产品决定。思考形成已确认的功能要求后，其现行正文进入 spec；doc 保留理由并回链。架构说明中的目标边界、当前实现与已运行检查分别标明。

采用编号组织时，只按需要建立以下分段；这些分段都不能替代 spec：

| 段 | 职责 |
|---|---|
| `00-产品与原则/` | 长期产品定位、目标用户与原则；与 README 摘要回链 |
| `10-架构与运行/` | 当前架构、模块职责、运行与验证说明 |
| `20-能力参考/` | 外部研究、实测、来源许可和能力边界 |
| `30-路线图/` | 长远方向和阶段安排；执行状态回链工单 |
| `40-版本实施方案/` | 某版本或专项如何分批交付、依赖、验证与收口；引用现行 spec |
| `90-归档/` | 被取代、放弃或只供追溯的材料，标明后继入口 |

`doc/决策档案/` 只记录同时满足难逆转、无上下文会困惑、有真实权衡的决定；保留取代关系与索引，不替代当前规格。`doc/经验笔记.md` 记录可修改且下次仍会复用的“现象 + 做法 + 证据”。两者均按实际内容惰性创建。

### 工单、实施方案与 CHANGELOG

- 未确认的需求可留在对话或 investigation issue。事实、用户决定、范围和验收充分后才进入 ready；仍有调查问题不因已有文档而自动升级。
- Issue 管理范围、状态、负责人、依赖和证据历史；正文维护当前结论并回链唯一规格，评论保留过程。PR 说明这次实现与验证。无独立追踪需要时不强制建工单。
- 实施方案管理一次交付怎样展开；当前功能要求进入 spec。已经完成但仍有维护用途的方案可保留并标明状态，仅因完成不能判定为归档。
- 持续发布且有使用者可感知变化的项目维护 Keep a Changelog 格式的 `CHANGELOG.md`；未发布变化进入 `Unreleased`，版本以实际 tag 或 registry 为准。一次性原型、私人脚本或内部生成物可按用途豁免，不倒填历史，不复制 Git log 或未来承诺。

## 4. 工程与验证前提

根据下一步工作确定需要的技术栈、运行边界、状态写入所有者、公开接口、持久化与外部副作用。只做足以支持本轮的设计；细节由 agent 收口，会改变产品意图、成本或风险的取舍才需用户决定。

- 运行环境、依赖、配置来源、安装／启动／构建／测试入口以实际文件核实；没有的明确列为缺口，不复制参考项目的命令。不保存凭据值或个人环境。
- 项目已要求功能开发前建立检查时，将其作为进入相应实现的前提；没有这类要求时依据真实风险判断，不普遍强制架构检查器或统一工具链。
- 已有架构检查须说明策略权威、实际纳管模块、允许依赖、差异基准、新旧违规、例外维护责任及未覆盖部分。自建检查须有正确放行与拒绝的样例证据；零源码通过不表示架构或产品已经验收。
- 缺少必要保障时，列明建设动作及阻止的具体工作，由正常工程实施承接；规范整理不冒充工具已经可用。不得刷新基线或放宽规则掩盖新增违规。
- 验证回到用户／调用者完整路径，覆盖相关失败、取消、恢复、持久化或权限边界。结构检查、模拟验证、真实外部能力、视觉判断和人工接受各有证据范围；未运行或环境受限保持未验证。

## 5. 存量迁移

已有项目纳入初始化或规范迁移时，以本标准为目标主动整理；只读巡检报告迁移缺口。仅有旧命名或既有布局不能作为豁免依据。迁移不授权改产品行为、删除数据或扩到未选定项目。

1. **锁定来源与当前要求**：核对实际工作区、用户指定版本、已确认决定、文档、实现和验收记录；识别生成、嵌套、历史及外部引用边界。
2. **按内容建立映射**：分别列出现行功能要求、共用设计、词义、架构／研究／理由、交付安排和历史，映射到新职责。混合文档拆分有效内容，保留出处；不把旧版本方案整体改名为 spec。
3. **处理差异**：核实哪些要求被后续决定取代、哪些已实现但未验收、哪些仍待实现。事实冲突自行查证，用户决定冲突才对齐；保留已排除内容的历史身份，不能重新启用。
4. **先验证候选**：在隔离位置准备迁移候选并检查内容覆盖、来源、链接与含义；切换前原权威保持可用。候选明确为非现行，不让读者同时消费两份有效正文。
5. **同步切换正文与消费者**：在同一受控变更中更新新正文、AGENTS、根／分层 README、spec／doc 导航及相关技能引用。受影响正文由对应维护动作同步；已获远程写入授权时同步工单引用，否则报告待办，不能声称已同步远端。
6. **退出旧维护路径**：无消费者且无独立历史价值的重复正文清理；历史材料按归档职责保留并标明后继。仍有实际外部消费者时只保留必要的迁移指引，写清消费者及退出条件，不继续维护旧正文。受保护原件保持原样，通过外围索引说明关系。
7. **复核完整路径**：从需求到共用规则、实现入口与验证依据检查可达性、唯一性及未完成边界。范围内仍有旧现行消费者或未处置重复正文时只能报告部分迁移；历史引用与有退出条件的指引分别说明。

普通局部改动不自动变成全项目迁移。发现旧权威时先读取以保全要求，按当前授权迁移受影响部分；整体迁移不足时回报给 setup 的选定范围，不将一次局部修改称为全项目迁移完成。

## 6. 完成判断与例外

分别报告：本次检查／初始化／迁移做到了哪里，下一步具体工作是否具备前提。检查完成不等于迁移完成，迁移完成不等于产品通过验收。

已完成的授权范围应满足：

- 目标、排除项、当前要求与证据可找到，下一步缺口和依赖可解释；
- 每类内容由新职责对应的正文维护；当前正文唯一，导航与使用该内容的入口同步，旧维护路径已退出；
- 小项目裁剪和无界面／无领域概念等不适用项有实际依据；
- 工程入口与检查覆盖有真实证据，未建立、未运行和未验收部分明确；
- 全局与项目规则不混放，受保护范围、用户数据与无关改动未被覆盖；
- 修改、检查、真实运行、人工接受、提交与发布分别绑定证据。

明确用户指令、平台生成机制或嵌套所有权确需偏离时，记录依据、影响和维护方式；普通旧布局不是例外。迁移指引和兼容入口另须写明退出条件，避免成为永久平行体系。
