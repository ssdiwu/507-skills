# 项目初始化与巡检（setup）

给具体代码项目建立或校准长期协作规范。目标不是让所有仓库长成同一套目录，而是让下一位 agent 能从当前项目找到真实入口、权威关系、任务与安全边界、验证方式和外部动作授权。

巡检标准以本技能的 `references/project-standard.md` 为权威来源；执行前完整读取该文件。

## 覆盖什么

- 新项目需要建立最小但完整的协作规范；
- 老项目的 `AGENTS.md`、入口地图、文档职责或验证方式可能整体失真；
- 一个或多个已明确选定的项目需要统一比较规范质量；
- 需要识别规范生成文件、历史副本、冻结样本和项目自身维护的分层规则，避免误覆盖。

只维护 README、doc 导航或目录职责时使用 `507-map`；架构摩擦使用 `507-inspect`；业务代码 bug 使用 `507-fix`。

## 项目形态

巡检时先判断项目属于哪种形态，不能先套模板：

- **完整合同**：持续维护的应用、服务、库或多模块项目，存在多个运行边界、外部系统、持久化、安全风险、发布面或耐久文档。
- **精简合同**：单入口扩展、小型包、一次性原型或临时验证目录，职责和验证路径都很短。
- **受保护范围**：框架生成规则、嵌套项目自有规范、测试 fixture、冻结快照、worktree 副本、归档或历史 demo。除非用户明确点名并且维护方式允许，否则只记录，不改写。

选择能完整覆盖当前真实风险的最轻合同。精简不是省略安全、验证或外部动作授权；完整也不是复制全局工程纪律。

## 修改边界

默认只读并输出报告。用户确认落地后：

- `507-setup` 可修改项目级 `AGENTS.md` 及直接属于初始化合同的基础规范；
- README、`doc/README.md`、目录职责和地图结构交给 `507-map`；
- 术语或真实取舍未对齐时交给 `507-grill`；
- 已发现的业务代码安全缺口、bug、测试问题或架构摩擦分别转 `507-fix`、`507-test` 或 `507-inspect`，不得用规范文字伪装成实现已修复。

本 skill 不修改业务代码，不生成宿主专属配置，也不把报告授权扩张为跨项目批量写入。

## 输入范围

用户可提供一个或多个项目根目录。给出 workspace 时：

- 用户已经明确选定项目集合，就按该集合执行，不重复要求选择；
- 范围不明确时先识别仓库、生成/历史/测试边界，再请用户只决定真正需要纳入的集合；
- 不把 workspace 当成单一项目，也不自动修改扫描到的全部仓库。

## 巡检流程

### 0. 读取项目标准

完整读取 `references/project-standard.md`。目标项目有明确例外、现成地图或生成机制时，记录其来源和优先级，不凭样例覆盖。

### 1. 冻结范围与写入所有权

确认项目根、Git worktree、当前工作区状态、目标文件、排除项和完成信号。识别生成文件、嵌套规范、历史副本、测试样本、归档与并行 worktree；同一 worktree 只保留一个写入负责人。

### 2. 扫描项目现实

先读根 `README.md` 与 `doc/README.md`（存在时），再读 `AGENTS.md`、manifest、入口、构建/测试配置、目标代码和安全相关配置。通过实现和可运行配置核对：

- 项目类型、平台、入口与真实消费者；
- 本地/远端副作用、凭据、持久化和迁移边界；
- 实际存在的验证命令；
- 文档声明与当前行为的冲突；
- 已经存在但尚未修复的安全或可移植性缺口。

### 3. 选择合同形态并核对规范

逐项检查：

- `AGENTS.md` 是否只保留跨任务稳定且项目特有的定位、阅读路由、任务/失败边界、工程/安全约束、验证和外部动作授权；
- 平台、命令、路径和能力是否能由 manifest、源码或运行证据核实；
- 是否混入版本号、当前分支、Issue、端口、服务器、临时任务、个人绝对路径、凭据值或一次性进度；
- 是否机械复制全局工程纪律、Skill 路由表、长文档地图或旧初始化模板；
- 现存实现若违反安全目标，是否明确写成“当前缺口 + 阻断 + 修复出口”，而不是笼统声称安全；
- README、CHANGELOG、doc 地图、术语、决策与分层 README 是否按真实消费者和项目形态存在，而不是为形式完整创建；
- 当前实现、路线图、规格、Issue、变更日志和归档是否各有唯一职责并正确回链。

### 4. 输出巡检报告

```md
# 项目初始化与巡检报告

## 总览
| 项目 | 项目形态 | AGENTS | 入口地图 | 文档职责 | 验证入口 | 受保护范围 | 安全/事实缺口 | 推荐动作 |

## 项目详情
### <project>
- 当前现实与证据：...
- 建议合同形态：完整 / 精简 / 保持受保护
- 规范漂移：...
- 文档与实现冲突：...
- 现存代码风险及阻断：...
- 排除项：...
- 推荐路由：...

## 建议执行顺序
1. ...
```

每项结论给出文件、配置、代码或命令证据。没有真实内容时不建议创建空目录、空术语表、空 ADR 或空经验笔记。

### 5. 经确认后路由落地

- 项目级 `AGENTS.md` 合同 → 本 skill 在已授权范围内更新；
- README、doc 导航与目录地图 → `507-map`；
- 术语、产品或风险取舍 → `507-grill`；
- 需求规格或远程工单 → `507-prd` / `507-issue`；
- 代码风险、测试或架构问题 → `507-fix` / `507-test` / `507-inspect`。

一次只处理用户确认的项目和文件。发现范围外问题只保留脱敏证据，不自动扩大交付。

## 验证

落地后至少检查：

- Markdown 链接、相对路径、围栏、尾空格和 `git diff --check`；
- 文档中的命令、manifest script、平台和入口真实存在；
- 动态版本/阶段、个人路径、凭据值、旧模板标记和重复权威已从目标规范移除；
- 受保护范围没有意外 diff；
- 文档没有把未运行的构建、测试、联网或人工验收写成通过。

纯文档改动不虚构业务测试结论；若发现的代码风险未获修复授权，验证的是“风险已被准确标注和阻断”，不是“实现已经安全”。

## 红线

- 不未经确认重写项目规范或批量修改 workspace；
- 不把同一套通用模板复制到所有项目；
- 不覆盖生成文件、嵌套权威、冻结样本、归档或历史 worktree；
- 不修改业务代码，不以规范文字掩盖现存实现风险；
- 不为形式完整创建空文件或强制迁移已有清晰文档结构；
- 不把动态状态、个人环境、凭据或宿主专属调度写进共享项目合同；
- 不执行未经授权的 commit、push、tag、publish、deploy 或外部系统写入。

## 完成与接力

- **完成信号**：选定范围均已按项目形态检查；事实、缺口、受保护范围和建议合同有证据；授权的规范已落地并验证。
- **产物**：全量巡检报告，以及授权范围内的项目合同修改；业务代码风险保持独立、可接力的证据边界。
- **候选出口**：地图进入 `507-map`；代码/测试问题进入 `507-fix` 或 `507-test`；架构问题进入 `507-inspect`；需求或治理项进入 `507-prd` / `507-issue`；落地后进入 `507-review`，明确要求提交时再进入 `507-commit`。
- **回退条件**：项目规则互相冲突、生成所有权不明或需要用户选择治理方向时进入 `507-grill`，不自行覆盖当前权威。
