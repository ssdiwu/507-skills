# 项目初始化、规范迁移与巡检（setup）

让下一位没有参与前期讨论的人或 agent 找到项目目标、当前要求、共用规则、真实入口和验证依据，并判断下一步工作是否具备前提。新项目直接建立这套依据；已有项目核对存量后迁移到同一标准，旧目录和旧约定本身不是保留理由。

执行前完整读取唯一标准 [`references/project-standard.md`](references/project-standard.md)。标准定义文档职责、适用条件、工程前提和迁移要求；本文件负责范围、动作、权限与交付。按用户请求也可单独建立或校准全局 `AGENTS.md`，不把项目事实带入全局规则。

## 覆盖与边界

- 新项目：检查目标、下一条完整用户路径及其设计和工程前提，建立已确认的协作基础；未知项给出影响和下一动作。
- 已有项目：识别仍有效的要求、实现与验证差异，逐项说明旧内容应由哪份新正文维护，在授权内同步正文与引用，并退出旧维护路径。
- 只读巡检：检查同一标准，报告证据、缺口和迁移建议；发现不符合项不自行写入。
- 全局规则：只在用户明确指定宿主、文件或目标位置后处理；保留跨项目稳定的沟通、工作与安全规则。

仅处理全局规则时，只核对指定文件、用户确认与相关宿主依据，应用标准中的全局约束及对应验证；跳过项目根、用户路径、文档迁移和工程检查步骤。不得因为当前目录存在项目就顺带纳入。

本 skill 负责项目工作依据的建立与校准。具体产品取舍由 `507-grill` 对齐，功能规格由 `507-prd` 维护，导航由 `507-map` 校准，检查工具建设与业务实现进入正常工程工作。只改某个 README 或地图时直接用 map；架构体检用 `507-inspect`，已知 bug 用 `507-fix`。

## 范围与授权

先核对当前请求和已有授权，区分查看、拟议方案与实际初始化／迁移。用户已经明确要求在选定范围内落地时，说明处理范围后连续完成，不在同一授权内重复要求确认；只读请求保持只读。只有目标、权威归属、成本或风险出现实质取舍时进入 grill。

- 确认项目根、当前 worktree、分支、本地改动、指定或最新确认的基线、目标文件与排除项。涉及远端协作时核对相关远端分支；未核实的部分明确说明，不自动切换或合并。
- 用户已选定项目集合时直接采用；仅给出 workspace 且范围不清时，先识别仓库与受保护边界，再请用户决定纳入集合。不把整个 workspace 当成一个项目。
- 全局规则的目标位置必须明确。可参考仓库根 [`templates/AGENTS.global.example.md`](../../templates/AGENTS.global.example.md)，不得猜测宿主路径或自动覆盖个人配置。
- 同一 worktree 同一时刻只有一个写入者。保护无关改动、用户数据、凭据、生成产物、嵌套项目、冻结样本和历史副本；生成文件通过其生成源维护。

在已授权的项目范围内，setup 可修改 `AGENTS.md` 及直接属于初始化的基础规范，整理或迁移已确认的术语、共用设计约束；不得借整理内容自行决定产品行为或视觉方向。地图、具体规格和其它正文按下述职责接力。迁移授权覆盖范围内的必要引用同步与旧入口退出，不自动扩大为业务代码、工具配置、其他项目或远程写入授权。

## 工作流程

### 1. 读取现实与已有共识

从项目规范、根 README 和实际文档导航进入，读取本轮相关的设计、术语、规格、长期参考和用户确认；再核对 manifest、代码入口、配置、测试与运行证据。没有代码的新项目如实记录尚未建立的入口，不从旧封档或参考项目复制能力声明。

区分已确认目标、当前实现和实际验证。发现冲突时核查来源、后续决定和证据；当前实现不能自动取代已确认要求。可查事实自行查明，工程细节由 agent 收口，只有用户拥有的取舍需要对齐。

### 2. 选择需要的规范范围，检查下一步工作前提

按项目实际风险，选择下面足够支持工作的规范形式；不增加没有用途的文档：

- **完整合同**：持续维护的应用、服务或库，存在多个运行边界、持久化、外部系统、发布面或跨会话协作。
- **精简合同**：职责单一、入口和验证路径较短的工具或原型；可以合并少量说明，仍采用新职责与安全边界。
- **受保护范围**：生成规则、嵌套权威、第三方原件、fixture、冻结快照、归档或其它 worktree；只识别，除非被明确纳入且维护方式允许。

逐项核对目标与排除项、下一条完整路径、共同语言、共用设计、现行规格、长期知识、工程与验证入口。每项记录依据、已成立／缺口／不适用、对下一步的影响和承接动作。无界面、无领域术语或无长期材料时按条件裁剪，不创建空文件，也不把老项目留在旧标准。

必要工程保障由项目技术栈、风险和已确认规则决定。已有检查要核实覆盖与有效性；缺少必需检查时明确它阻止哪一步，将建设交给正常工程实施，不自动引入跨项目检查器。允许开展的设计、隔离验证和产品实现分别判断，不因某项缺口阻断全部独立工作。

### 3. 建立依据或迁移存量

新项目只将已有充分依据的内容写入对应入口；产品目标或技术能力仍未知时，保留缺口并进入相应证据或决策动作，不补造完整设计。

已有项目按标准的“存量迁移”执行：核对有效内容，建立来源与目标映射，先验证候选，再同步切换正文权威、导航和消费者引用，最后清理重复正文或归档历史。迁移中保留来源、未实现要求和未验收边界；旧版本方案不能整份改名后冒充现行规格。

按内容职责接力，已有授权不重复询问：

| 内容 | 承接动作 |
|---|---|
| 协作规则、已确认术语和共用设计约束的整理归位 | setup 在授权范围内更新基础规范 |
| 根／分层 README、spec 与 doc 导航、迁移后的入口关系 | `507-map` |
| 当前功能要求、失败边界和验收正文 | `507-prd`；小改可直接更新已有规格 |
| 尚未确定的产品、设计或风险取舍 | `507-grill`；事实不足先进入 explore／research／prototype |
| 研究、架构说明、理由、规划或历史正文 | 授权的对应文档维护动作；只归位时保持含义，地图由 map 同步 |
| 工程检查建设、业务缺口或测试问题 | 正常工程实施，或 `507-fix`／`507-test`；架构调查进入 `507-inspect` |
| 远程工单与证据回链 | 已获对应远程写入授权时进入 `507-issue`，否则列出待同步项 |

切换后应只有一份现行正文。迁移尚不完整时报告剩余消费者、阻塞和下一动作，不能以“已建立新目录”宣称迁移完成。这些动作在同一请求内分别维护对应内容，不要求用户记忆技能名称；setup 不接管后续全部实施。

### 4. 验证并交付

- 检查 Markdown 链接、相对路径、锚点、围栏及 `git diff --check`，确认受保护范围和无关改动未被覆盖。
- 检查有效要求、已排除内容和来源关系没有在归位时遗漏或改义；旧现行引用已更新，历史引用被明确区分。
- 从“找到需求 → 读取共用规则 → 找到实现入口 → 找到验证依据”走查一条实际阅读路径；没有实现时明确缺口，不伪造入口。
- 对授权且可运行的相关检查记录实际结果、配置和覆盖；未运行、失败、零源码通过、模拟验证和真实环境验收分别说明。纯文档检查不证明业务已经可用。
- 核对全局规则不含项目事实、个人路径、动态状态或宿主机制；项目 AGENTS 引用真实入口，不重复维护命令表、目录地图或全局纪律。

报告按实际内容裁剪，全局目标未涉及时删除相应部分：

```md
# 项目初始化／迁移／巡检结果

- 范围与基线：...
- 全局目标、来源及授权（涉及全局规则时）：...
- 项目形态与受保护范围：...
- 本轮结果：已检查／已初始化／已迁移／部分完成，附实际证据
- 下一步条件：可开展的具体工作；被阻塞的工作及原因

| 检查项 | 当前依据 | 已成立／缺口／不适用 | 对下一步的影响 | 承接动作 |
|---|---|---|---|---|

## 迁移结果（有存量时）

| 来源与有效内容 | 唯一目标 | 已同步引用 | 旧入口处理 | 未完成事项 |
|---|---|---|---|---|

## 验证与接力

- 已运行及结果：...
- 未验证或未授权范围：...
- 下一动作与依赖：...
```

报告用于本次交付，不建立第二份长期项目状态表。只读巡检完成不代表迁移完成；初始化完成也不代表所有产品实现前提或最终验收已经满足。

## 完成与接力

- **完成信号**：只读巡检在选定范围核查完成且证据、缺口齐备时结束；初始化或迁移须完成授权范围内的落地和验证，现行正文与入口唯一、旧维护路径已退出；单独全局任务以指定规则及其对应验证完成为准。仍有阻塞时如实报告部分完成和接力条件，不称落地完成。项目下一步开工条件另行判断。
- **产物**：本次结果与证据、授权范围内的基础规范和各职责接力形成的修改；检查结论、迁移结果和开工条件分别成立。
- **候选出口**：只读结果可直接交付；缺口进入上述对应动作；规范行为变更后由 `507-review` 独立只读审查；仅明确要求时进入 `507-commit`／`507-release`。
- **回退条件**：事实不足先补证；已确认决定冲突或维护所有权不明时停止依赖它的写入并对齐，继续独立工作；保留已验证基线，不用候选或旧实现静默替换。
