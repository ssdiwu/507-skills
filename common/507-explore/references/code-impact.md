# 代码行为改动的影响调查

当用户已有一个具体行为改动，而入口差异、状态归属或上下游影响尚未查清时，使用本参考。保持 explore 的只读边界；产物进入当前会话快照，不建立另一套项目状态库。简单改动已有充分证据时直接复用，不强制填矩阵。

## 从行为定位当前实现

先写清本次准备改变哪种用户可观察行为、哪些行为必须保留，以及正在读取的版本。编码前可能还没有差异；空的工作区差异不代表没有影响需要调查。

从项目入口、相关契约和测试开始定位。已有功能索引、依赖图或搜索结果只提供线索，路径、符号和语义要回到当前代码核实。先读直接相关的一层关系，只有尚未找到写入者、调用者或恢复路径时再扩展；契约与测试无法解释行为时继续读实现，不把受限阅读变成遗漏证据的理由。

区分改动落在显示、选项来源、草稿与默认值、校验、正式提交、持久化或恢复中的哪一处。对不同用户入口分别追踪，不用“共用组件”推断它们具有相同默认值或副作用。

## 需要查清的关系

| 对象 | 需要取得的当前证据 |
| --- | --- |
| 用户入口与草稿 | 哪个动作进入；谁维护尚未提交的选择；默认值从哪里来 |
| 校验与正式提交 | 在哪里拒绝或接受；哪个命令或服务真正接受写入 |
| 状态与派生视图 | 哪个组件负责哪份状态的正式写入；其他页面、缓存或索引怎样读取，以及何时失效 |
| 持久化与恢复 | 何时写入、何时读回；重连、重启、失败或旧结果晚到时如何处理 |
| 下游消费者 | 哪个行为依赖本次变化；关系成立的语义理由与文件、符号或运行依据 |

同一个字段名、导入关系或目录不能单独证明产品关系。尚未确认状态怎样同步时，继续标为未知；分别说明草稿、乐观显示、运行时事实、快照和缓存的来源，不把它们视为同一份状态。

根据已经发现的影响决定继续读什么：必须核查的直接路径、值得核查的相邻调用者或使用者、特定条件下才有关的路径、只需保持不变的行为，以及只提供线索的证据。每个判断写清原因；被排除的分支需要有条件或不变量支持，不能把没读到当作不受影响。

## 交给下一步的最小证据

在已有探索快照中补充：

- 本次改变的行为、版本与已读范围；
- 各入口的草稿、校验、提交、状态归属和保存／恢复差异；
- 必须保留的行为、关键影响关系及定位证据；
- 待核实事实、确需用户决定的取舍，以及代表性的验证场景。

必要时用一张入口对照表或 Mermaid 表达关系；不为每个任务生成完整表格。规划中的测试、已有测试文件、已经执行的测试与实际覆盖分别标明。

发现索引失真时报告需要修正的条目，在只读探索中不改索引。影响已足以支持下一步时，事实充分则返回原任务；产品取舍交给 grill；技术假设需要观察时进入 prototype；发现明确故障则进入 fix。未知尚未核实时，不把调查结果伪装成完整实施计划。
