# 代码改动的工程设计与既有检查

本参考用于把已确认需求转成状态责任、接口、调用顺序和验证方案，也可由正常实施直接使用；读取它不代表必须启动 grill 或重新向用户提问，也不扩大调用它的动作所拥有的修改权限。只对齐或只审查时产出设计与缺口；只有实施或相应文档写入已获授权时，才修改代码、契约或配置。出现用户拥有的产品、权限、成本或风险取舍时才返回决策对齐。局部改动已有契约和验证依据时沿用，不为形式完整另写设计文档。

## 编码前应能解释什么

读取目标项目的规则、现行规格、相关公开契约、直接调用者和测试；无法确认状态或副作用时继续查看实现。已有影响调查直接复用，过期部分重新核实，不要求先调用某个技能。

| 判断 | 工程设计需要说明的内容 |
| --- | --- |
| 行为与依据 | 哪项已确认需求支持此次变化；哪些用户可见结果和失败语义需要改变或保留 |
| 状态所有权 | 每份可变事实由哪个组件接受写入；按什么身份或隔离键划分；草稿、缓存和派生视图如何与它保持一致 |
| 复用路径 | 已有命令、服务或公开接口能承担哪些工作；若新增路径，为什么当前路径不足 |
| 跨边界调用 | 按项目实际分层确定职责、允许的依赖方向和公开入口；外部副作用在哪里执行 |
| 时间与恢复 | 仅对相关异步行为说明事件顺序、重复请求处理、过期结果规则、取消、重试与恢复边界 |
| 迁移与验证 | 受影响消费者、存量数据或兼容条件、退出条件；用哪个已有验证入口或测试接缝，通过哪个场景判断结果 |

一份正式状态由一个组件负责接受写入，不等于整个系统只允许一个全局对象。派生状态可以存在，但必须说明它从何而来、何时更新与失效；不得让草稿或乐观视图成为第二个接受正式写入的队列。

对不同客户端、运行环境或交付方式，只检查项目真实存在且被本次改动影响的差异，不凭参考项目增加模式。不强制任何语言、层名、文件名、代码行数阈值或模块模板。

## 保存到最近的现有载体

简短改动可在实施说明中交代上述适用判断。需要跨会话继续约束交付时，更新已授权的现有设计、实施说明或契约；PRD 只保存产品行为与验收，工单只摘要并回链。事实、拟议设计和用户已确认决定分开，不建立第二份完整需求或全局决定日志。

实施已获授权且存在跨模块或状态归属变化时，在引入新调用关系前同步相应契约。权限不足或关键假设未验证时保留缺口并路由，不把草图当成已经成立的架构。

## 使用目标项目已有检查

先读实际脚本或配置，确认检查做什么、基于哪个差异范围、覆盖哪些模块、是否会写入基线或其他文件。复用与风险相称的只读检查，在需要基线对照时于修改前后运行；没有对应检查时报告缺口并使用已有行为验证，不自动建设新的跨项目工具链。

工作区差异、提交差异和分支差异可能对应不同入口，使用与本次任务一致的基准。结果分别记录：实际覆盖范围、已有违规、新增违规、显式例外、执行失败和未检查部分。未纳管模块、未解析的依赖形式或未运行检查不能写成通过；结构检查也不能证明状态归属和时序语义正确。

已有违规属于可追踪的现状，不自动成为本次接受它的理由。修改基线、扩大例外或降低规则强度需要明确的范围与审查依据，不能用刷新基线来消除新增失败。检查器不会证明的部分，回到用户路径、公开契约及失败／恢复场景验证。
