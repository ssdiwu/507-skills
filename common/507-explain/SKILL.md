# 概念解释（`explain`）

把一个用户不理解的概念讲到真正理解。目标不是罗列完整知识，而是用最短定义和必要示意，让用户正确理解概念所指的对象与关系。

`507-explain` 做的是：**不懂的概念 → 清晰、可复述的理解**。

## 覆盖什么

- 技术概念、方法论、行业术语、缩写与框架名词；
- 两个或少量相近概念的差异与边界；
- 需要通过流程、状态变化、层级、映射或组件关系才能讲清的概念；
- 代码、写作或日常对话中出现的通用理解障碍。

## 不覆盖什么

- 定位项目里的问题、代码机制、证据与未知 → 用 `507-explore`；
- 系统调研一个外部项目、文章或参考实现 → 用 `507-research`；
- 对齐一个方案中的用户决策 → 用 `507-grill`；
- 系统学习整个主题、建立学习计划或长期知识工作区 → 不在本技能范围。

## 核心纪律

1. **讲懂，不讲全**：成功标准是用户能够形成正确心智模型或用自己的话复述核心，不是覆盖概念的全部历史、分支和进阶用法。
2. **先短后深，定义必须落地**：先用一句白话定义建立锚点，且定义里的每个名词都要能指向用户可辨认的事物；做不到就先给一个可想象的具体场景，再从场景里提炼定义，不用一组抽象词替换另一组抽象词。仍有理解缺口时，再逐步增加比喻、反例、相近概念对照或技术细节。
3. **从用户已知出发**：能从上下文判断背景时直接适配；背景差异会实质改变解释方式时，才一次询问一个简短问题。
4. **一次聚焦一个核心概念，说明未解释的术语**：相关概念只在解释当前核心所必需时引入。每个引入的未解释术语必须三选一——现在讲、标为黑盒（说明它负责什么、现在不需要懂、可在下一轮展开）、删掉并重写这句话；不把回答扩成术语瀑布，也不留下既没解释又没标记的隐藏债务。
5. **示意服务理解**：存在三项以上映射、依赖步骤、状态变化、分支、层级或多方交互时，优先使用一个最小可用视觉；简单事实或一步关系不机械画图。解释未成立时按《解释未成立时的升级顺序》逐层排查，不跳过构造与表达直接换更重的载体。
6. **区分事实与类比**：明确哪些是概念本身，哪些只是帮助理解的比喻；不能让类比反过来制造错误规则。
7. **默认不落盘**：解释完成即结束。只有用户明确要求，或该词已经成为项目稳定术语时，才按项目规则写入术语表。

## 选择示意方式

只选择最能降低理解成本的一种，不同时堆叠多种重复图：

| 关系形状 | 首选形式 |
|---|---|
| 精确字段映射、少量概念对比 | 表格 |
| 三步以上流程、状态变化、分支或多方交互 | `Mermaid（图表语法）` 流程图、状态图或时序图 |
| 小型层级或纯文本更清楚的结构 | 结构化列表 |
| 单一事实、一步动作、一个定义 | 简短文字说明，不画图 |

只使用当前渲染器支持的 `graph/flowchart`、`stateDiagram`、`classDiagram`、`erDiagram` 与 `sequenceDiagram`；需要其它类型时改用受支持的 `flowchart`，或退回表格与结构化列表。

图后用一两句指出读图重点；不把图中所有文字再完整复述一遍。当前界面不能可靠渲染 `Mermaid（图表语法）` 时，退回结构化文字或表格，不生成 `ASCII（字符图）`，也不同时输出图表与等价字符图。

## 解释未成立时的升级顺序

用户仍不理解时，按成本从低到高依次排查，不跳层。载体是最后一层，不是第一反应。

| 层 | 先查什么 | 修法 |
|---|---|---|
| 一、构造 | 定义是否只是抽象换抽象；引入的术语是否都有归宿 | 定义换成可指认的名词或改从场景提炼；未解释术语补讲、标黑盒或删掉重写 |
| 二、表达 | 一张图是否塞了太多、缺分层与焦点；缺的是否其实是行为证据 | 拆成多张递进小图、加分层与强调；改用真实运行输出、中间状态或反例对照 |
| 三、载体 | 障碍是否属于感知型——量级比例、连续变化，或需要用户亲手调一下才有直觉 | 属于感知型才生成临时视觉件；不属于则说明缺的不是载体，路由到 `507-explore`、`507-research` 或 `507-grill` |

第三层的临时视觉件遵守两条约束：写在系统临时位置，不进项目工作树、不进版本控制；交付时说明它是一次性产物与清理状态。要留下可分发的视觉成品时，这已超出本技能，交给视觉制作技能。

## 工作流程

1. **识别用户卡住的核心概念**：确认用户真正卡住的是哪个词、关系或差异；能从上下文确定时不反问。项目特有术语先读项目术语表与相关权威定义，通用概念不为形式完整漫扫项目。
2. **给最短定义，或先给场景**：默认一句话说明“它是什么”，避免用更多未解释术语定义它；用户对该概念完全没有直觉时，先给一个可想象的具体场景，再从场景里长出定义。
3. **选择解释路径**：根据概念形状与用户背景，在场景、比喻、反例、对比或最小视觉中选择最有帮助的一种。
4. **检查易混淆的边界**：说明一个最容易混淆的“不是什么”或相近概念差异，防止用户只记住比喻而误解概念。
5. **按反馈迭代**：用户仍未理解时按升级顺序换一种解释方式，不重复同一套措辞。用户说不清卡在哪时，主动给出两到三个最可能的卡点让他指认，而不是问“懂了吗”；理解成立就停止。

## 输出形态

简单概念可以只有两三段。复杂概念按需使用；用户对该概念完全没有直觉时，把 `放进场景` 提到 `一句话` 之前，让定义从具体例子里长出来：

```md
## 一句话
<最短白话定义；每个名词都可指认>

## 示意
<一个表格或 Mermaid 图；确有必要时才用>

## 放进场景
<一个具体例子>

## 容易混淆
<它不是什么，或和相近概念的关键差异>
```

## 与相邻技能的边界

| 技能 | 分工 |
|---|---|
| `507-explain` | 用户不理解一个概念 → 讲懂 |
| `507-explore` | 项目问题尚未看清 → 读取证据，确定认知边界与下一步 |
| `507-research` | 外部参照物 → 核实机制并判断借鉴意义 |
| `507-grill` | 已知前提下的用户决策 → 追问并收束 |

## 红线

- 不用更多未定义术语解释当前术语；
- 不留既没解释又没标为黑盒的隐藏术语债务；
- 不用一组抽象词替换另一组抽象词充当定义；
- 不为展示完整而扩成系统课程；
- 不把类比当成事实边界；
- 不用无助于理解的装饰性图表；
- 不在构造与表达两层尚未尝试时直接生成视觉件，也不把临时视觉件写进项目工作树或交付无清理状态的文件；
- 不替项目探索、外部调研或决策对齐执行。

## 完成与接力

- **完成信号**：用户当前卡住的概念已有可复述的最小心智模型，关键边界和最易混淆点已说明，且过程中引入的术语都已解释、标为黑盒或移除。
- **产物**：对话中的解释与最多一种必要示意；默认不落盘。确有感知型障碍而生成临时视觉件时，产物在系统临时位置，附一次性说明与清理状态，不进项目工作树。
- **候选出口**：理解成立后返回调用它的原任务；发现项目事实未知时进入 `507-explore`；需要外部证据时进入 `507-research`；真正问题是用户取舍时进入 `507-grill`；只需解释时直接结束。
- **回退条件**：用户仍不理解时换解释路径，不重复堆同义措辞或继续扩大课程范围。
