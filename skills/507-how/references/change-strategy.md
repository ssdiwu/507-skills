# 跨约束变更策略

当介入点穿过接口、可变状态、存量数据、权限或多个消费者时采用。只写当前策略需要的部分，不把每次局部变更升级成全库架构设计。

## 从用法判断边界

用真实调用路径说明调用者要完成什么，它现在必须知道哪些内部条件。接口包含类型、顺序、不变量、错误与恢复，不只是函数参数。

抽取或替换后检查调用者能少知道哪件事：若仍要手工初始化、刷新缓存、追踪重复队列或协调清理，复杂度可能只是搬了位置。设想删除抽象后复杂度会消失还是在各调用处重现；真实复用、变化原因、生命周期或副作用边界成立才保留。没有消费者和公开契约的内部旧路径可清理，但须有指定范围、调用链、配置与存量数据的核对证据。

## 所有权、并存与切换

| 关系 | 当前策略须能回答 |
| --- | --- |
| 正式状态与派生状态 | 谁接受正式写入，谁生成缓存/草稿，失效、同步和恢复由谁负责 |
| 数据与资源生命周期 | 创建、更新、删除、取消与清理由谁拥有；失败会留下什么 |
| 权限 | 谁能在什么条件下做什么，拒绝、撤销和恢复会发生什么 |
| 多入口与消费者 | 哪些入口写，哪些消费者读；入口差异是否影响校验、提交或恢复 |
| 新旧并存 | 并存期间哪一路有效读写，如何避免两个权威，各消费者何时切换 |
| 旧路径退出 | 哪个可观察信号允许退出，支持中的兼容或存量数据如何处理 |
| 失败保全 | 失败前可用状态是什么，如何恢复，结果未知时怎样对账而不盲重试 |

表格可以直接放进项目既有策略或规格，不另建竞争状态台账。既有决定与实现不一致时分清缺口；实现现状不能删除已经确认的要求。只读方案描述改变，不因此执行改变。

## 选择可拒绝策略的验证

把推荐的成立条件变成观察：什么结果会让它不值得做或必须改方向。内部简化先建立公开行为、错误、时序、持久化与生命周期的基线；行为变化使用已确认目标的前后结果。不能把推荐强度当实施证据，也不能用单元测试通过证明所有外部行为不变。

切片按依赖与风险安排，不按文件数平均拆分。先建立足以验收的候选及回退点，成功后再替换有效基线；跨消费者变化先验证一个完整使用路径，再推广有共同条件的部分。数据迁移覆盖当前存量读回和失败恢复；并发、异步或重试风险回到原动作的时序分支。

最终验证穿过受影响的入口、正式提交、持久化、页面或输出与恢复，按实际环境报告未覆盖。独立审读消费当前差异、需求与证据，问题返回原实施者；既有检查仍对应版本时复用，不为形式重复全库验证。

## 可消费的交付

策略至少让执行者知道目标与介入点、改变与保持、调用者用法、所有权、选定路径与理由、必要切换/退出、验证与失败处理。项目已有规格或计划可承载这些信息，不要求固定模板。

仅策略请求交付到此；父目标已授权实施时继续实现、同步直接消费者、检验完整路径。新公共行为或责任决定确实超出原范围时保留具体影响，完成独立且明确的工作，再回交最小实质取舍。
