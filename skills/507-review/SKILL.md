# 独立交付审查

对指定实现、文档、作品或明确变更，判断是否符合已确认要求和项目规则、是否存在有证据的质量风险。审查者须独立于本次实施；自己修改过的范围只能自查，需要另一执行者完成独立结论。

只读：不改受审源码、测试、文档、配置、规则、基线或持久状态，不补测试、不代修、不提交。一次性报告可在对话交付；持续审查主动维护允许的独立证据位置，不写受审内容。先分别确定受审对象和允许写入的证据位置：受审对象之外不等于任务范围之外也可写。复制、探针、日志、缓存和清理都受本次位置与数据归属限制；只允许报告时不据此扩成任意验证文件写权。没有可写证据位置时采用不落盘检查或保持未运行；明确不写任何文件时仅会话交付。

## 范围与依据

按用户指定的对象和核验目标确定基准。核验现有实现时，以指定材料、实际版本与已确认要求为依据，不因没有提交差异转向最近提交。审查变更时，优先用户指定提交、分支、标签、差异或路径；未指定时核对工作树、暂存／未暂存及相关未跟踪变更，无当前改动则审分支相对已核实主干，仍无可用基准才使用最近提交并说明局限。工作树干净不等于无差异。确认不了基准时说明缺口，不能给猜测范围判通过。

读本次适用的项目规范、实际阅读入口、现行规格／issue（工单）、测试配置与有关决策，说明所用版本、差异范围及未覆盖。没有明确需求来源时标明该缺口，仍核对范围蔓延、行为风险与可验证性，不把个人偏好包装成项目规则。

多轮确认、最新状态或组合目标影响结论时，核当前有效要求与完整目标；关键来源截断则补读相关部分或保留未知。既有授权与依赖、新报告与实证分别判断，不能据未读、旧报告或子步骤通过给整体目标放行。

区分执行者自报与工具回执，审查者口述采用规则也不能作为完整读取证明。未提交源文件用实际指纹定位，不能当成 HEAD 代码；后续修改不自动继承旧审查通过。

对完整首次使用或相连流程的结论，核有效目标的起点及测试准备是否旁路了用户必需动作。绑定、配置或确认被预置时，后段可在其实际范围通过，该目标动作仍未验证；不据此放行完整目标，也不将明确只验中段的任务扩成全产品审查。

## C 的独立职责与领域检查

Agent 承担 C 时以本能力为核心；共有资源提供方法，不是检查者。实施者切换技能、提示词或模型仍是自查，不因标签成为 C，也不要求独立者必须换模型。C 核 A 的验收是否忠实覆盖原目标，测试全绿不能掩盖遗漏要求。

可核验并利用 B 的证据，再独立完成必要检查，不要求所有动作全部重做。结论绑定实际受审版本；后续修改需复核受影响内容。既定三层协作中发现交协调者安排修复；C 不直接修受审产物，转为修复者后该范围须由另一 C 核验。

非代码交付采用相称领域方法：主稿、用户手改与目标文件按[作品合同](references/shared/artifact-contract.md)检查；事实、引语、作者判断与承诺按[作者与来源](references/shared/author-and-source.md)检查。内容检查不能由编译替代，工具不足保留未覆盖；作者审美和用户最终接受另列。

## 判断与取证

选择必要检查或判定验收覆盖前，完整读取[可观察验收](references/shared/validation.md)，据此确定检查与结论范围。判断真实调用、写入、最终消费、原动作或运行版本时（包括运行测试及解释结果），在取证或下结论前完整读取[工程证据](references/shared/engineering-evidence.md)。两者均可复用已完整读取且版本未变的内容；未触发的分支不展开。

| 视角 | 本次问题 |
| --- | --- |
| 规范 | 是否违反有效项目约束，公开入口／权限变化是否同步必要说明 |
| 要求 | 目标、条件、排除和失败边界是否实现，自动检查是否能拒绝代表性错误结果 |
| 质量 | 有证据的逻辑、状态、竞态、安全、错误处理、性能或维护风险，具体影响哪条路径 |

跟实际风险读相连片段，证据不足才扩到下一相关位置。另一种设计或更少文件不自动成为缺陷；架构偏好要连接真实调用者负担、状态协调或验证困难。严重性与置信度分开，后果严重但证据不足的假设标为待核。

运行检查前核实完整动作的副作用：命令本身、运行目录、复制输入、探针文件、日志、字节码/缓存、清理及外部调用。原件没有变化只能证明原件保全，不证明这些动作获准。优先采用可在允许范围内完成的只读检查；例如 Python 导入检查须抑制字节码写入。确需隔离副本时，只有本次写权覆盖其位置和内容才建立，保留源版本；不能用示例路径替代这项判断。

需要命令日志与可选指纹时，可使用包内 check_run。它会创建日志和回执，并运行给定命令；不是无副作用工具。下面只说明参数形状，路径和命令必须按本次许可确定后才能执行：

```sh
python3 scripts/check_run.py --argv-json '<已核实命令的参数数组>' --cwd '<允许检查的位置>' --log-dir '<获准写入范围内尚不存在的新目录>' --timeout 60 --source '<检查位置内的源文件>'
```

argv（参数数组）不通过 shell 拼接。日志目录已存在时组件拒绝覆盖，应选择获准范围内的新位置或核对已有证据；不得为了重跑示例先删除固定路径。清理仅处理本任务创建且归属已核实的对象，仍需遵守当前写权。退出 0/1/2 分别表示命令成功、命令失败、输入或准备错误，不裁决业务、授权或独立性。无法在许可范围完成的检查保持未运行并说明具体影响，不借补证扩权。

## 条件性共有方法

| 条件 | 读取与用途 |
| --- | --- |
| 指定版本、来源身份或旧报告需要核实 | [事实与来源](references/shared/evidence.md)：区分事实、推断和读取范围 |
| 新证据反驳旧发现、发现已修或需要返回 | [权威与返回](references/shared/authority-and-return.md)：更正当前结论并回交原实施者 |

发现涉及多状态或跨主体时序、仅文字难以辨认影响时，可采用 `507-visualize` 呈现已核证据与未验证条件。图解仍受本次只读及证据写入范围限制，不修改受审对象，不因图可解析就认可故障可达或验收通过。

## 结论与结束

按原始要求交付范围、基准、依据、覆盖、发现和验证限制，区分要求数、样例数、测试断言通过数与现行要求符合数；不同判定依据的结果分别报告，断言与现行要求不一致的测试即使通过，也不计入要求符合数。说明每项检查实际支持哪些结论；部分检查不足或失效，不否定其余有效证据，也不能据部分通过放行全部要求。每项发现给可定位的文件／符号／行为、判断依据、影响、严重性与确定程度、必要下一动作。没有阻塞发现时写清“未发现阻塞问题”及其范围，不宣称产品接受或发布就绪。

复核时逐项说明原发现是已修复、被证据否定、属于已确认的预期行为，还是仍未解决，并给出依据。修复凭相关证据关闭，误报明确撤回，预期行为说明确认依据；已回复不等于已解决。仍未解决项保留状态与影响，无新证据不重复提出同一发现。

明确范围已按规范、要求与质量审完，有证据的结论即完成；审查请求可结束，父目标则将发现或结论返回。已有协调层时修复交回协调者安排，否则交回实施负责人，修改后仅对相关变化独立复核。基准、规格或证据不充分时保留未知与未检查，不以自报或猜测放行。

本次出现真实中断、上下文压缩或转交时核实际版本、写权、有效尝试与未完成；普通结束跳过时，读[真实中断、交接与续办](references/shared/continuation.md)并在本职责原权限与完成边界内采用。

本次目标需要对齐产品功能、入口与用户操作的设计／实现／运行差距时，读[交互点与证据](references/shared/interaction-map.md)。需要独立的可探索地图结果可按原权限委托 `507-product-map`；普通策略、规格或审查不强制建图，结果回到当前职责。
