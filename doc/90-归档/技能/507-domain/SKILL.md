# 领域建模

作为次要工作能力，承接可独立请求或由目标、方案、规格、实现任务提出的领域建模工作。结果是当前范围内可供后续设计、实施与验收使用的概念、关系和必要约束；原任务的整体目标与最终交付继续由原负责人持有。

共有依赖从[共有资源合同](../../lib/README.md)开始：首次读取参考前，用 `skill_document=$(realpath <本文件路径>) && test -f "$skill_document" && cat "$(dirname "$skill_document")/../../lib/README.md"` 打开合同，参数取当前实际读取的 SKILL.md 路径；其余引用统一按合同解析，已完整读取且未变化的合同直接复用。 持有多阶段原任务时，局部动作完成后按[阶段返回](../../lib/README.md#阶段返回)核对指定交接并继续。

## 输入、范围与权限

承接当前任务、业务范围、有效决定、术语与行为依据，以及获准读取的实现材料。先核项目入口和相关文档，已有充分定义直接使用；只读取会影响当前概念判断的部分，不从数据库字段或代码类名直接推定业务模型。

当任务需要建立或修订概念、辨别一词多义、确定身份和归属关系，或概念冲突已经影响目标、方案、规格或实现时采用。普通概念解释、查阅词表、文字润色和按充分定义实现功能直接完成，不因涉及业务名词就增加建模步骤。仅要识别问题时交付问题与依据，不自行决定新词义。

沿用原任务授权。咨询、方案讨论和明确只读请求不自动授权修改项目文件；需要写入但未获授权时交付拟议定义和具体归宿。已有文档维护授权则及时更新成立部分，无需为每个词重复确认。建模本身不增加修改代码、数据库、公开接口、外部平台或安装发布的权限。

## 从场景校准概念

1. **定位分歧与适用范围。** 把用户表达、现有词义、有效规则和实现事实分别列清。先判断词是否处于相同业务范围；不同业务范围的同名概念可以各有含义，明确上下文与跨范围映射，不强行统一全项目叫法。缺少事实先按[事实与证据](../../lib/methods/evidence-and-decisions/evidence.md)查证。
2. **提出可辨认的定义。** 对影响当前任务的含糊或重载词，提出清楚的叫法、含义、适用范围与必要排除，保留同义词和旧称的对应。用例子与反例区分相邻概念；用户用词和既有定义不同，先核上下文，再说明冲突，不能把 Agent 建议写成定案。
3. **推敲关系与约束。** 沿真实任务核相关对象怎样关联，按需要检查身份是否延续、谁归谁、允许几个、何时建立或解除关系、状态怎样变化及哪些条件必须保持。只展开会改变当前设计的维度，不预造完整分类体系或套用固定架构模式。
4. **用场景检验。** 选择能区分候选模型的正常、例外或边界情况，写清前提、涉及的对象和预期结果。假设场景注明是假设，不当作实际发生的业务事实。例如判断“取消”作用于整个订单还是某个订单项，可以追问只取消其中一项后，其余项目与订单身份应怎样保留。按[可观察验收](../../lib/methods/evidence-and-decisions/validation.md)检查场景是否真能拒绝错误模型。
5. **核对实现与决定。** 涉及“现在就是这样”的陈述时，读取相关代码、测试或运行证据；没有实现或不可访问时保留未核实范围。有效要求与实现相反时标明实现差距，不用现状覆盖要求。事实可查就查，常规可逆选择由 Agent 处理；产品含义、责任或实质成本风险取舍沿[决定归属](../../lib/methods/evidence-and-decisions/decision-ownership.md)处理，只有会改变当前决定的未知才按[问题依赖](../../lib/methods/evidence-and-decisions/question-frontier.md)询问。

## 记录与原任务接续

概念或关系成立时，按[权威与返回](../../lib/methods/evidence-and-decisions/authority-and-return.md)核对已有定义、取代关系与直接消费者，在原授权内及时更新当前正文。定义变化影响有效需求、数据身份或公开契约时，明确受影响位置及尚需决定的兼容或迁移问题；不把命名讨论直接变成代码重构。

| 内容 | 保存位置与边界 |
| --- | --- |
| 稳定词义、适用业务范围、别名与必要排除 | 项目已有术语权威，如 `GLOSSARY.md`（术语表）；不混入实现细节、讨论过程或完整行为规格 |
| 关系约束、操作规则、状态变化及验收场景 | 项目现行规格或对应模型说明；一份当前正文，其他位置回链 |
| 重要选择的原因与替代项 | 项目决策依据；仅当改变代价显著、脱离背景难以理解且确有替代方案取舍三项同时成立时采用 ADR（架构决策记录） |
| 未决、候选与证据缺口 | 当前任务已有讨论或过程记录；与已确认定义分开 |

沿用项目现有文件格式与多业务范围组织方式；没有相应权威时，仅在已有具体内容、确需持久维护且获授权时建立最小记录。不预建空词表、统一目录或第二份领域模型总账。领域内容已经解决且父任务仍有授权工作时，携结论继续规格、方案或实现；不循环转交或等待重复批准。

关系确实难以用文字理解时可按需采用 `507-visualize`；图表回链事实或方案依据，画图本身不证明模型正确。相邻技能不可用时按同一职责直接完成所需结果，不以安装为前提。

## 完成与恢复

- **完成信号**：当前范围内影响后续工作的概念与关系已可一致解释，代表场景没有未解决的关键矛盾；定义、要求、实现与假设可区分，授权内的文档更新已读回，或只读结果已清楚交付。
- **产物**：与任务相称的领域定义、关系和约束、能检验边界的场景、依据与剩余未知，以及实际文档差异或拟议更新。不强制图表、全套模型文档或 ADR。
- **返回**：说明结果怎样影响原任务及还有哪些动作未完成；父目标继续，独立建模请求在约定范围完成后结束。模型已澄清不等于代码已实现或业务已验收。
- **回退条件**：关键取舍未定、证据冲突或访问受限时只报告成立部分及受阻关系，不称整体建模完成。保全已有有效定义，说明最小取证或决定动作，继续不受阻部分。
