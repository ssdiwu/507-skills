## 1. 总体结论

**三层分工成立，应当保留。当前 85 候选的划分方式不可执行，应当收缩。**

四点核心判断：

1. **主要／次要／共有三层是正确的职责切分，不是入口数量预算。** 证据在 `spec/技能分层与共有资源.md:546`「三层不是固定串行步骤」、`lib/methods/decision-ownership.md:456`「内部技能、方法或子任务结束后，原任务负责人继续核对未完成目标」。这两句把"能力完成 ≠ 目标完成"写进了共有方法，而不是留在某个总控里，正是我担心的"引入总控后 Agent 更难完成任务"这一风险被正确规避的证据。

2. **真正的问题不在分层，在"候选 → 可运行入口"这一步被跳过了。** 85 个候选里 0 个是已实现的包，只有 2 个包存在。历史试跑的 12 份输出中，选中的是 `method-fix`/`method-review`/`method-organize`/`method-verify`，而这四个**都不是已实现的包**。也就是说：**被验证的路径全部落在未实现的候选设计上，已实现的两个包从未被独立验证过执行效果。** 这是本轮最重要的发现。

3. **`state_diff.py` 的默认用法可以被产出者自己放行**，这正是问题 6 担心的失败模式。我实测确认：产出者写一条 `basis: "我决定了"`（甚至 `basis: "x"`）即可让受保护字段变更返回 exit 0 / PASS。README 已诚实写明"不能把它的PASS写成意图确认"，但**组件设计上没有阻断自放行，而调用流程里也没有第二来源的核验环节**。

4. **独立审读者漏检是真实且可复现的。** `review.json` 对 work r2 明确写"没有发现新增日期或身份取代方面的明确错误"，而这正是该轮的两处实质错误。漏检在 5 分钟后的 `corrected-review.json` 中被补上（新增 `WORK-R2-DEADLINE-SUBSTITUTION`、`WORK-R2-ACCEPTANCE-STATE-LOST`）。**这证明"给一位独立审读者"不足以作为验收闸门**，需要先校准评分器（与 `optimization-data.json` 的 `measure` 阶段一致）。

## 5. 共有规则如何被真正消费（问题 3）

**当前状态：共有规则是"被读过"，不是"被消费"。**

证据（`readFiles` 交叉表）：work_v2 r1 读了 authority-and-return.md + validation.md → PASS_SCOPE；creation r1 读了 evidence.md + authority-and-return.md → **FAIL**（主稿仍写"相关文章"）。

即：**读过方法 ≠ 用上方法**。失效点在"读到正文"到"落到具体字段/句子"之间。

**建议的三级消费契约**（按强度递增，可机械检查）：

1. **引用级**（现状）：正文链接 + "何时读"。只能证明可读。
2. **动作级**（建议）：方法条目必须写成**可勾选动作**，例如 authority-and-return.md 第 1 步已经做到了"每项须有去向"——把它变成输出结构里的**必填字段**（`infoLedger: [{claim, target, field, disposition}]`），没有这个字段就不算消费了方法。
3. **拒绝级**（最强，建议用于两个已知失败点）：给定一个**具体错误结果**，当前检查是否会拒绝？这是 `lib/methods/validation.md:513` 已有的要求，但没有任何工具实现它。

**最小可执行改动**：为 `work-update` 路径引入 `infoLedger` 必填字段。它同时解决三件事——条件/缘由遗漏（r1）、身份澄清升级为字段授权（r2）、未撤销状态丢失（r2）。

## 6. 自主性与约束的平衡（问题 4）

## 8. CLI 与语义的分工（问题 6）

**必须交给 CLI（确定性、可机械判定）**：
- 字段级快照对账与受保护字段变更 → `state_diff.py`（修 D2/D3 后）

**必须留给语义判断（不可自动化）**：
- basis 是否构成真实授权
- "16日之前"是否取代了精确字段
- F2/F3 是否同一实验

**如何核定"不是产出者自填 basis"**：
1. **`allowedChanges` 只能由被调用方之外的一方生成**（政策文件由人或独立审读者写，不由产出者写）。
2. basis 引用**原话片段**而非结论描述；工具可机械校验"引用片段确实出现在输入中"。
3. `artifact.check` 的 PASS **只在其 scope 字段内**有效；任何把它当"意图确认"的用法在 review.md 中应被标记。

**适合**：找反例、核对跨消费者一致性、检查"规则是否被读到却没用上"、审查记录与代码是否一致（本次 D6/D7 即由我独立发现）。

## 13. 验收方法

**正例**（必须通过）：C-02、C-04、C-05；r3、creation-heldout、fix、fix-verified。

**反例**（必须被拒）：C-01、C-03、C-06；work r2、creation r1。

1. 全新任务，无历史答案，不提供既有错误反馈；
2. 执行者只拿任务 + 包 + 授权，不拿 `catalog-v2.json` 这类设计索引；

4. 至少 3 个不同领域（工作更新 / 创作 / 工程）各 1 例。

**达标 / 停止 / 回退**：

- **回退**：保留可用基线包；候选不覆盖已可用包；任何关键值误改即回退。
