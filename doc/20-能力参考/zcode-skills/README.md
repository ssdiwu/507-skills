## 上游的具体价值

**架构治理提供开工前的工程判断。** 它要求明确状态由谁接受写入、复用哪条现有路径、跨模块从哪个公开契约进入；异步工作还要交代顺序、重复处理、过期结果与恢复边界。受限阅读从相关契约、规格和测试开始，证据不足时再扩大。依据是 [主说明](upstream-29628c9acdb81/.agents/skills/architecture-governance/SKILL.md) 与 [AI 实现指引](upstream-29628c9acdb81/.agents/skills/architecture-governance/references/ai-guidance.md)。

**功能边界分析提供围绕具体行为的影响证据。** 它分别追踪各个用户入口，经草稿、校验和提交动作，找到真实状态所有者、持久化与恢复；共用 UI（用户界面）组件不等于共用默认值、提交结果或保存位置。关系按语义与当前源码核验，不能只根据导入关系推断。依据是 [主说明](upstream-29628c9acdb81/.agents/skills/feature-boundary-planner/SKILL.md)、[影响简报模板](upstream-29628c9acdb81/.agents/skills/feature-boundary-planner/references/impact-brief-template.md) 与 [源码发现指南](upstream-29628c9acdb81/.agents/skills/feature-boundary-planner/references/source-discovery.md)。

上游功能边界技能还包含 `impact-only`（只分析）、`planning`（规划）和 `implementation-handoff`（实施交接）三种模式。后两种模式涉及产品决策、规格和用例规划，直接引入会与本仓库的 `507-grill`、`507-prd` 等动作重叠。

## 已核实的机制边界与缺口

1. **严格治理范围有限。** 实际策略注册 15 个模块，仅 `storage` 设置 `managed: true`，其余 14 个为 `false`，并启用 `managedOnly: true`。检查器会跳过未托管模块的主要逐文件检查；存在治理脚本不能证明全仓已经受控。[策略原件](upstream-29628c9acdb81/architecture-policy.yaml) · [检查实现](upstream-29628c9acdb81/scripts/architecture/index.mjs)
2. **检查器不能证明所有架构性质。** 解析器只解析已发现源码间的相对导入，工作区包名、路径别名和动态导入需要其他证据；状态所有权与异步时序也依赖工程判断和行为验证。[规则目录](upstream-29628c9acdb81/.agents/skills/architecture-governance/references/rule-catalog.md) · [策略解析](upstream-29628c9acdb81/scripts/architecture/policy.mjs)
3. **改动范围有特定含义。** `--changed` 读取相对 `HEAD` 的工作区差异和未跟踪文件，不代表某个已经提交的分支差异。已有违规基线与新增违规分开报告，不能为了通过检查自动接受新的基线。[检查实现](upstream-29628c9acdb81/scripts/architecture/index.mjs) · [排障说明](upstream-29628c9acdb81/.agents/skills/architecture-governance/references/troubleshooting.md)
4. **文字要求比部分机器检查更广。** 技能要求托管模块提供 `module.ts`、`contract.ts`、`contract.example.ts` 与 `CONTRACT.md`，当前 `missing-module-artifact` 检查只显式要求前两个。生成的上下文主要是相关路径清单，不是完整语义验证结果。[模块合同](upstream-29628c9acdb81/.agents/skills/architecture-governance/references/module-contract.md) · [检查与上下文生成](upstream-29628c9acdb81/scripts/architecture/index.mjs)
5. **公开文档存在缺口。** 功能边界技能与种子图引用的 `docs/skills/feature-boundary-graph.md` 不在该 revision 的完整公开文件树中。原件保留这一引用，没有补造该文档；核验结果写入 `reference-audit.json`。
6. **种子图只核验到文件存在。** 图中 39 个不同源码路径都在该固定提交中；本次没有逐一验证符号与行为，也没有运行产品流程或测试。文件存在不能证明图中关系成立或测试已覆盖。
7. **这不是可独立运行的工具包。** 相关脚本引用 `typescript`、`yaml`，并依赖目标仓库的源码、策略和执行环境。本次保存源码用于研究，没有安装它们或运行架构检查。上游 `NOTICE.md` 中指向其他产品源码的链接也不属于本次完整收录范围。

## 关联程度与采用建议

复核按触发、输入、产物、修改权限与停止位置比较；目标和产物重叠时优先改进既有方法，只有共享检查维度时不据此合并整个技能。下表记录融合前的关联分析；实际落点与修订状态以[融合与验证](融合与验证.md)为准。

| 上游能力 | 现有承接位置 | 关联判断 | 建议融入或替代什么；整体替代会丢失什么 |
| --- | --- | --- | --- |
| 功能边界的只读影响分析 | [507-explore](../../../common/507-explore/SKILL.md) | 高：已有入口、上下游和证据范围追踪职责 | 可用逐入口、校验、提交、持久化和恢复追踪，具体化代码行为调查分支；不能整体取代还服务写作、项目认知和开放未知的 explore |
| 功能边界规划中的未定义行为与取舍 | [507-grill](../../../common/507-grill/SKILL.md) | 高：都要查清前提并收敛用户拥有的决定 | 用代表性场景、差异入口与有依据的用例裁剪增强代码场景追问；保留原有决策依赖、冲突处理和唯一归宿 |
| 规格与验收用例 | [507-prd](../../../code/507-prd/SKILL.md) | 高：已有行为、失败边界与验收责任 | 可细化准备条件、动作、断言和证据的写法；保留产品问题、用户故事及唯一当前规格，不引入独立用例文档流水线 |
| 实施交接 | 正常实施；需要耐久追踪时使用 [507-issue](../../../code/507-issue/SKILL.md) | 部分：交接结果有承接者，但 issue 不是逐文件实施计划 | 当前工程设计交给执行者；issue 保留可领取的目标、范围、证据和验收，不能把上游交接模板整体塞入 issue，也不能用它替代远程生命周期管理 |
| 状态所有者、复用路径、契约与时序设计 | 正常实施；[507-grill](../../../common/507-grill/SKILL.md) 的工程责任边界 | 高：现有合同已明确 agent 自行补全接口、实现切片和验证方案 | 可补充工程设计应回答的具体问题；没有独立技能名称不等于缺少这项职责，不能强迫已明确的需求先进入 grill |
| 识别重复所有者、平行路径和边界泄漏 | [507-inspect](../../../code/507-inspect/SKILL.md) | 中：检查维度重叠，任务目的不完全相同 | 融入架构摩擦的观察依据；不能丢失接口深度、删除测试、调用者负担、证据候选与 simplify 交接 |
| 行为不变的简化与验证 | [507-simplify](../../../code/507-simplify/SKILL.md) | 中：所有权和路径收敛可辅助设计 | 将适用问题用于已有重构记录和行为基线；保留修改、验证及带证据关闭责任，不能用治理说明替代实际简化 |
| 改后架构检查与新旧违规区分 | [507-review](../../../code/507-review/SKILL.md) | 检查步骤高度关联，整体范围不同 | 可具体化架构质量审查和覆盖范围报告；review 仍须检查需求符合度、安全、错误处理及其他真实质量风险 |
| 长期规则、入口与验证命令的核实 | [507-setup](../../../code/507-setup/SKILL.md) | 部分：已有规范接入责任 | 可核实已有架构策略的权威、实际覆盖和验证入口；不能因此把检查器开发、基线批准或持续策略维护都视为 setup 已覆盖 |

当前更支持先融合方法、替换相关方法段，再通过真实任务观察剩余缺口。上游原件尚不能完整替代上述任何一个技能；部分流程可以成为既有代码场景分支的主体，而不只是追加几条原则。已确认并落实的合同与验证边界见当前融合记录。

需要单独保留的缺口是“可执行架构规则、检查器与违规基线的建立及维护”。现有只读审查技能不能直接承担这类写入；setup 也未承诺完整覆盖它。是否需要独立治理技能，要先明确这是不是目标，以及怎样适配目标项目的语言、工具和既有约束。仅保存了 ZCode 的脚本不足以证明通用治理能力已经成立。

## 先前方案候选（过程参考）

| 方案 | 组织方式 | 收益 | 代价与适用条件 |
| --- | --- | --- | --- |
| A：完全吸收 | 把影响追踪和治理方法补进 explore、grill、review、setup 等既有入口 | 新入口为零，适合希望维持最少技能名称的体系 | 方法分散，多个现有合同需要协调；容易把一般探索变成重型分析 |
| B：只新增影响分析 | 功能影响作为独立动作；架构治理作为项目规则及现有实施、审查流程的检查内容 | 新入口少，直接补具体行为的影响证据；适合架构稳定、治理规则较少的项目 | 开工前的工程判断没有独立交付入口，依赖各项目和实施流程持续承接 |
| C：两个收窄的独立动作 | 分别承担具体行为的影响分析、已确认改动的架构边界设计 | 当前事实与拟议设计各有明确产物，便于正常实施与独立审查消费 | 与 explore 和既有工程设计责任高度关联；须先证明独立触发与交付的收益，不能只为两个上游名称增加入口 |

此前对 C 的优先推荐已撤回。现行 explore 已承担入口与上下游调查，grill 也明确工程设计由 agent 自行收口；新增独立名称不足以证明新增能力。当前应先按上述关联分析形成融合候选，核对既有能力是否保留，再评估尚无合适承接者的治理机制。最终采用保持现有技能入口的方法融合，复用项目已有检查；不建设跨项目检查器，也不新增 impact 或 architecture 入口。

`507-impact` 与 `507-architecture` 仅作候选名称，没有创建或启用对应技能。

## 场景与验证边界

以下场景用于检查职责与验证下一轮实际任务效果：

- **共用组件、提交行为不同：** 分析应逐入口查证，不能把一次组件调整推成多个功能同步改行为。
- **异步结果晚到与恢复：** 设计应明确状态所有者、结果生效条件与恢复依据，验证回到可观察行为。
- **纯文字或局部样式调整：** 应直接完成适度验证，不强制运行完整影响与架构流程。
- **图索引过时、契约缺失或未纳管模块：** 应报告缺口与实际覆盖范围，不能用路径存在或脚本绿灯替代证据。
- **规格与实现冲突：** 应分别记录事实和已确认决定；涉及产品意图时返回决策对齐，不能静默改规格迁就实现。

验收看的是实际报告有没有少查、越权、重复产物或误报完成；本次完成合同走查与局部检查，尚未进行跨模型的实际任务效果回放，具体边界见融合记录。它们能约束影响分析与工程设计，界面观感和连续工作体验仍需要各项目自己的设计依据与实际体验验收。
