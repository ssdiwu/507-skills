# 507-rednote 产品需求

状态：已实现并完成本地验证，待提交。

本需求落实[小红书图文采用视觉摘要合同](决策档案/0013-小红书图文采用视觉摘要合同.md)，其中“视觉摘要”和“动态图片槽”采用[项目术语表](术语表.md)的定义。当前公开行为以 `write/507-rednote/SKILL.md` 及其机器规格为准，本文作为需求与验收基准。

## Problem Statement

当前 `507-rednote` 以成熟主稿的完整保真和连续长文分页为核心，逻辑块不等于物理页，脚本按真实高度自动把正文填入多张图卡。这能保存文章完整性，但会让单页承担多个段落，页面结构受连续文本支配，不利于把每张图卡做成一眼可理解、视觉焦点明确的社交内容。

现有能力也只交付静态小红书图卡，不能在保持同一图文构图的前提下把图片位置替换成实况照片；同一视觉内容需要公众号封面时，也缺少 `21:9` 主封面与 `1:1` 分享封面的独立构图和组合检查。

## Solution

`507-rednote` 改为观点型社交视觉包：从成熟来源提取中心判断、关键证据和最有传播力的观点，每张图卡只承担一个观点，视觉表现与单页理解速度优先。图卡不再承诺容纳主稿全部承重内容，但所有入选观点必须可追溯到来源，不能歪曲原意；未进入图卡的内容必须明确进入帖子正文、配套文案或不采用清单，不能静默消失。

同一套视觉结构支持三类交付：

1. 小红书静态图卡：封面加逐页单一观点，保持 `3:4` 画幅。
2. 小红书实况照片：在静态图卡的图片位置中放入用户提供的短视频，交付可发布的 Live Photo（实况照片）及可检查的静态首帧。
3. 公众号封面对：基于同一中心判断分别构图 `21:9` 主封面和 `1:1` 分享封面，并提供组合预览；不生成公众号正文。

## User Stories

1. 作为内容作者，我希望一篇成熟文章被提炼为一组一页一个观点的图卡，从而让读者在信息流中快速理解并愿意继续翻页。
2. 作为内容作者，我希望清楚知道哪些原文内容进入了图卡、哪些保留在帖子正文，从而避免平台适配歪曲文章或静默漏掉关键证据。
3. 作为内容作者，我希望系统根据内容表达选择稳定的视觉系统与页面结构，从而得到真正适合本篇内容的设计，而不是只更换配色。
4. 作为拥有短视频素材的作者，我希望把某张图卡的图片位置替换为实况照片，从而保留动作或现场证据，同时不破坏整组图卡的视觉关系。
5. 作为同时发布公众号的作者，我希望从同一中心判断获得独立构图的 `21:9` 与 `1:1` 封面对，从而不必裁切小红书封面或在方图中硬塞长标题。
6. 作为交付接收者，我希望每次拿到的图卡、实况照片和封面对都来自当前规格并通过自动与视觉检查，从而不会误用过期产物。

## Product Requirements

### 1. 视觉摘要合同

- 输入仍应是已成立的书面作品或已经确认的逻辑文案；选题、素材挖掘和长文成稿继续由上游能力负责。
- 每组内容必须先确定一句中心判断，再选择若干能共同支撑该判断的观点。
- 每张正文图卡只承担一个观点；例证、对比、步骤或数据可以作为该观点的证据，不得形成第二条竞争主线。
- 封面只负责建立主题和阅读承诺，不同时展开多个正文观点。
- 每个入选观点和关键视觉证据必须映射回来源；验收检查“入选内容是否忠实”，不再检查“原文全部承重内容是否进图卡”。
- 规格必须记录未进入图卡的重要内容及其去向：帖子正文、配套文案、后续系列或明确不采用。
- 不得为了填满画面编造观点、数据、步骤、标签或装饰性信息。
- 不设固定页数目标。页数由入选观点决定；内容不足时减少页数，观点过多时压缩选择或拆成系列，不通过缩小字号维持页数。

### 2. 视觉系统与页面结构

- 视觉系统、主题配色和页面结构是不同层次：视觉系统规定排版语言，主题规定颜色与材质，页面结构承接当前观点的内容形状。
- 每组内容只使用一套主视觉系统，不能逐页随机换风格。
- 首批视觉系统应至少覆盖编辑杂志与瑞士国际主义两种不同表达立场：前者服务叙事、观察和图片证据，后者服务数据、比较、流程和明确判断；内容主题本身不强制绑定其中一种。
- 页面结构必须由观点和证据形状决定。封面、判断、对比、流程、清单、数据、截图证据、图片证据和结尾可以使用不同结构，不能让所有页面退化为标题加卡片。
- 样式选择必须同时检查封面和正文，不能只凭封面效果决定整组样式。
- 图文叠加时必须先识别主体与安静区，标题不得遮挡人脸、关键产品、界面文字或证据焦点；最终按手机缩略图尺寸检查可读性。
- 应用界面、网页、终端和代码截图必须以完整可读为优先，默认使用等比包含和稳定留白，不按普通照片方式随意裁切。

### 3. 小红书静态图卡

- 静态图卡保持 `3:4` 画幅，封面和正文页使用稳定、连续的文件命名。
- 图卡必须生成可独立检查的图片、整组联系表、单文件预览和渲染清单。
- 单页不得出现文字或图片溢出、标题与正文碰撞、页脚覆盖内容、不可解释的大面积空白或小于移动端可读下限的正文。
- 每页必须在渲染清单中记录它承接的观点、来源映射、使用的视觉系统和页面结构。
- 任何内容、素材、视觉系统或全局主题变化后，受影响产物必须重新生成；只有当前规格与渲染清单的新鲜度一致时才能交付。
- 现有连续长文分页不再属于公开产品合同。旧规格不得在新版本中被静默解释为视觉摘要；应明确拒绝并给出迁移提示，或由迁移过程把选中的观点转成显式图卡。

### 4. 动态图片槽与实况照片

- 动态图片槽只接受用户已经选定的短视频素材；系统不从长视频中自动寻找高光片段。
- 短视频替换的是既有图片位置，必须沿用该位置的比例、裁切、安全区和视觉层级，不能另起一套视频页面语言。
- 在打包实况照片前，必须先从视频生成与最终构图一致的静态首帧预览，并通过普通静态图卡的裁切、层级和可读性检查。
- 视频时长、编码、尺寸和 Live Photo 打包必须符合目标平台当前配置；平台约束应由可维护的配置表达，不在可见文案中暴露生产术语。
- 交付至少包含可发布的 Live Photo 包、用于排查问题的关键静态图与视频组成部分，以及平台和时长说明。
- 视频过长、过短、主体不明确或无法在既定图片槽中保持可读时，必须停止并要求用户提供合适片段或明确裁切重点，不能自行承担叙事取舍。
- 运行环境无法完成 Live Photo 打包时，静态首帧仍可作为未完成预览保留，但不得把它标记为实况照片交付完成。

### 5. 公众号封面对

- 公众号能力只消费已经确认的中心判断、标题和视觉资产，不重新编排公众号正文。
- `21:9` 主封面和 `1:1` 分享封面必须分别构图，不能从同一画面机械裁切。
- `21:9` 可以保留完整或接近完整的标题与主视觉关系；`1:1` 应保留核心对象和动作，必要时使用更短标题，避免缩小文字硬塞。
- 两张封面必须保持同一视觉系统、主题和识别资产，并生成组合预览检查它们是否像同一组作品。
- 交付必须分别验证两种比例的尺寸、文字安全区、缩略图可读性和当前规格新鲜度。

### 6. 失败与回退

- 来源作品缺少稳定中心判断时，返回上游成文能力，不以视觉排版替代内容决定。
- 观点之间不能共同支撑同一中心判断时，返回候选融合或用户决策，不强行拼成一组图卡。
- 缺少必要图片时，可以选择文本主导的页面结构，或路由到独立素材获取/图片生成能力；渲染器不得静默联网取图。
- 任何自动检查失败时，产物状态只能是“规格或预览已生成，交付未完成”。
- 视觉判断无法由自动规则确认时，以联系表、关键页和手机缩略图检查作为人工验收接缝，不以 validator（校验器）通过替代视觉审查。

## Implementation Decisions

- 保留“逻辑内容规格 → 本地浏览器渲染 → 图片与清单”的总体产品接缝，但逻辑内容从连续长文块改为显式观点页。
- 内容忠实度改为入选观点的来源映射与排除内容去向，不再使用原文全覆盖作为交付硬门。
- 静态图卡、动态图片槽和公众号封面对共用内容与视觉系统定义，但各载体拥有独立尺寸、媒体和验收配置。
- 自动视觉检查应建立在真实浏览器布局结果上，至少覆盖溢出、字体下限、视觉边界、标题间距、页脚碰撞、异常空白和媒体框裁切。
- 继续要求产物新鲜度清单；规格、素材和关键输出应具备可复验的摘要值。
- 外部参考项目只提供设计机制证据。实现必须保持原创，不复制其受 `AGPL-3.0` 约束的代码、模板、文档正文或资产。

## Testing Decisions

### Unit

- 规格验证：一页只能声明一个主观点；封面、正文、视觉系统、页面结构和媒体类型组合必须合法。
- 来源合同：所有入选观点都有来源映射，所有重要排除内容都有明确去向；不再要求原文全量覆盖。
- 迁移边界：旧连续长文规格不能被静默接受为新规格。
- 媒体规则：静态图片、截图和动态图片槽分别校验必需字段与不允许的远程资源。

### Integration

- 静态图卡 fixture（测试样本）能生成完整图片组、单文件预览、联系表和当前渲染清单。
- 两种视觉系统至少各有一个封面与正文 fixture，并能证明样式身份、页面结构和正文可读性不是只换颜色。
- 浏览器布局检查能对溢出、标题碰撞、页脚碰撞、字体过小和异常空白产生稳定失败信号。
- 动态图片槽 fixture 能从合规短视频生成首帧预览、媒体组成部分与可检查的 Live Photo 包；缺失依赖和非法时长走明确失败路径。
- 公众号 fixture 能分别生成 `21:9`、`1:1` 和组合预览，并证明方形封面不是宽封面的裁切结果。

### End-to-end

- 以一篇成熟作品完成“视觉摘要 → 静态图卡 → 联系表 → 强制验收”的完整用户路径。
- 以同一套内容和一个短视频完成“静态首帧确认 → 动态图片槽 → Live Photo 交付”的完整用户路径。
- 以同一中心判断完成公众号封面对，并在手机缩略图尺度验证两张封面的可读性与一致性。
- 每条端到端路径都必须核对规格与渲染清单的新鲜度；旧产物或缺少必要输出时不得报告完成。

## Acceptance Criteria

1. 一篇成熟作品能生成一组一页一个观点的 `3:4` 图卡，每页可追溯到来源，未入选的重要内容有明确去向。
2. 整组图卡采用一套可辨识的视觉系统，封面与正文结构有变化但保持统一；联系表和手机缩略图检查通过。
3. 自动检查能阻止溢出、碰撞、不可读字号、异常空白、错误裁切和旧规格产物进入完成状态。
4. 用户提供合规短视频时，系统能在不改变静态构图合同的情况下生成动态图片槽首帧和可发布的 Live Photo 包。
5. 用户要求公众号封面时，系统能生成独立构图且视觉一致的 `21:9`、`1:1` 封面对和组合预览。
6. 长视频提炼、实况拼图、公众号正文和发布操作不会被误认为本功能已支持。
7. 实现和交付物不直接包含外部参考项目的受限代码、模板、文档正文或资产。

## Out of Scope

- 把完整长文连续排入图卡，或保留视觉摘要与长文分页两套公开模式。
- 从长视频自动选段、变速、剪辑或生成叙事序列。
- 二宫格、三宫格、四宫格等多视频实况拼图。
- 公众号正文排版、文章上传、账号登录、发布和运营。
- 在渲染阶段自动搜索或下载网络图片。
- 单张海报、纯图片修图、完整视频生成或横向演示文稿。
- 复制或派生外部参考项目的代码、模板、文档正文和视觉资产。
